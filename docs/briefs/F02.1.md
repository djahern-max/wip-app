## F02.1 · Auth hardening patch
**Roadmap phase**: A (patch to F02; roadmap order unchanged) · **Blueprint refs**: §3 (principle 8), §11 · **Decisions**: D-15, D-16, D-17
**Status**: done (2026-09-17), 214 tests; owner browser pass pending (last acceptance criterion). D-18 CLAUDE.md sentence approved and applied.

### Goal
Close the gaps found in the F02 review while the auth tables hold no real users: firm authority becomes an explicit row, a stolen password alone can never enrol TOTP, credential changes end sessions, anonymous callers cannot flood an insert-only table, and no secret or credential field can leave the server by accident.

### In scope
**Firm authority (D-15)**
- New global table `firm_membership(id, firm_id, user_id, role, created_at)`, `role ∈ {firm_admin, firm_staff}`, unique on `(firm_id, user_id)`. Approved without `tenant_id`.
- `Principal.firm_role` and `Principal.firm_ids` come only from `firm_membership`. The derivation from `membership` is removed.
- For a user with a `firm_membership` in the tenant's firm, the per-tenant `membership` row grants **entry only**; the role that applies inside the tenant is the `firm_membership` role. Entering a tenant still requires a `membership` row, so `membership_created` and `tenant_enter` keep appearing in the client's `audit_log`.
- A `membership` row carrying a client role cannot be given to a user who holds a `firm_membership` in that firm, and the reverse. Enforced in the service that writes the rows, and tested.
- `firm_admin` endpoints to create, change, and remove `firm_membership`. Audited to `firm_audit_log`: `firm_membership_created`, `firm_membership_role_changed`, `firm_membership_removed`. The last `firm_admin` of a firm cannot be removed or demoted.
- `0003` data step: existing dev rows get a `firm_membership` derived the way F02 derived it, so nothing local breaks. Reversible.
- `scripts/create_user.py` bootstraps a firm and its first `firm_admin` without needing a tenant to exist.

**Enrolment by admin-issued link (D-16)**
- Users are created with no password. The admin receives a one-time link: single use, stored hashed, expires after 72 hours (environment config).
- Redeeming the link sets the password and, for a user with a `firm_membership`, enrols TOTP and shows recovery codes in the same flow. The account is unusable until the flow completes.
- A firm user with no TOTP enrolled cannot log in with a password; the response is the same generic failure as any other. The F02 path "firm role, password only, reach enrolment endpoints" is removed.
- Admin TOTP reset clears the secret and recovery codes and issues a new link. Admin password reset issues a new link.
- Client roles may still enrol optional TOTP from inside an authenticated session.

**Session invalidation**
- All of a user's sessions are deleted on: password change, link redemption, TOTP reset, `firm_membership` change or removal. Removing a `membership` clears `active_tenant_id` on any of that user's sessions pointing at that tenant.

**Throttling and audit hygiene**
- Per-IP throttle on login, TOTP verify, and link redemption: 20 failures from one IP in 15 minutes returns 429 for the rest of the window (environment config). Counted from `firm_audit_log`; no new table. Once an IP is throttled, one `ip_throttled` row is written for the window and further attempts write nothing, so an anonymous caller cannot grow an insert-only table without bound.
- Client IP is taken from the proxy header only when `TRUSTED_PROXY_COUNT` says a proxy is present; otherwise from the socket. Documented in OPERATIONS.md.
- `login_failure` for an unknown e-mail stores the SHA-256 of the normalized attempted address in `detail`, never the text (people type passwords into that field).
- `firm_audit_log` rows with a null `firm_id` are readable by `firm_admin` only. The column stays nullable.

**No credential or secret leaves by accident**
- Every response that includes a user is built from an explicit allow-list schema. Credential columns on `user` are deferred in the ORM mapping so they load only where the auth service asks for them.
- Suite-wide test: every JSON response body captured during the test run is scanned for the credential column names and for the stored values of them.
- `Settings`: encryption keys, database password, and any other secret have no default. The app refuses to start without them, with a message naming the missing variable and not its value.
- `.env` is gitignored; `.env.example` carries no key material. A CI step fails if `.env` is tracked. If `.env` was ever committed, say so under Discovered, regenerate the dev keys, and stop for the owner before rewriting any history.
- CORS: no cross-origin request with credentials is allowed; a preflight from a foreign origin asking for `X-Requested-With` is refused. Tested.
- The probe router is mounted by `tests/conftest.py`. The `pytest in sys.modules` switch is removed from application code.

#### Open question: how `membership.role` represents an entry-only row

| Option | Upgrade | Downgrade | Verdict |
|---|---|---|---|
| **(a) New enum value** (e.g. `firm_entry`) in `membership_role` | `ALTER TYPE … ADD VALUE` needs Alembic's `autocommit_block()` because a new value cannot be used in the transaction that adds it; then `UPDATE membership SET role='firm_entry'` for firm rows. | Postgres cannot drop an enum value: rename the type, create the old one, cast three columns (`membership.role`, `audit_log.actor_role`, `firm_audit_log.actor_role`) across, drop the renamed type; first map `firm_entry` back to the `firm_membership` role. | Rejected. The enum is shared with the audit `actor_role` columns; the Python `Role` enum would carry a value that is not a role (`tuple(Role)` feeds `ALL_ROLES` and the matrix); "do not invent synonyms". |
| **(b) Nullable `role` + CHECK constraint** | `ALTER COLUMN role DROP NOT NULL`; `UPDATE membership SET role = NULL WHERE role IN ('firm_admin','firm_staff')` after deriving `firm_membership`; `ADD CONSTRAINT ck_membership_role_client CHECK (role IS NULL OR role IN ('client_admin','client_pm','client_viewer'))`. | Drop the constraint; `UPDATE membership SET role = fm.role FROM firm_membership fm JOIN tenant t …` for null rows; raise if any null row has no matching `firm_membership` (cannot be reversed faithfully); `SET NOT NULL`; drop `firm_membership`. | **Proposed.** The database itself now forbids a firm role in `membership` (half of the mutual-exclusion rule); `Role` stays the five real roles; audit columns untouched; downgrade is total under the service invariant. |
| **(c) Leave the firm role in `membership.role`, ignore it** | Only create `firm_membership` and derive rows. | Drop `firm_membership`. | Rejected. Reproduces the F02 defect D-15 removes: the schema implies a per-tenant authority that does not exist, the value duplicates `firm_membership.role` and drifts on every role change, and an entry row for a firm user has no honest value to carry. |

**Consequences of (b) I intend to build (say if any is wrong):**
- `Membership.role: Role | None`. `None` = entry row. Effective role in a tenant = the `firm_membership` role when the row is an entry row, else `membership.role`. `Principal.role`, `session_payload.role`, `GET /api/session/tenants[].role`, and `actor_role` on `tenant_enter` all report the effective role.
- Service invariants (tested): an entry row (`role` omitted or null) may be written only for a user holding a `firm_membership` in the tenant's firm; a client-role row may never be written for such a user (`409`); a firm role in `membership.role` is refused (`422`) and the CHECK constraint backs it; `PUT …/memberships/{user}` on an entry row is `409`; creating a `firm_membership` for a user who holds any client-role row in that firm's tenants is `409`.
- ~~Removing a `firm_membership` also removes that user's entry rows in the firm's tenants, each with its own `membership_removed` audit row, one tenant context at a time inside the request transaction.~~ **Superseded by owner answer A** (separate transactions, one per tenant). Reason: without it a former staff member keeps rows that let them enter tenants with no role, and the downgrade of `0003` stops being total. Demotion (`firm_admin` → `firm_staff`) leaves entry rows alone.
- ~~The `0003` data step must lift `FORCE ROW LEVEL SECURITY` on `membership` for its own duration, and restore it.~~ **Superseded by owner answer B** (loop over tenants, set `app.tenant_id` per tenant, never unforce). It aborts with a named list if any user holds both a firm role and a client role inside one firm, since no derivation is honest for that user.
- To read a target user's `membership` rows from an admin request (invariant checks, cascade), the service sets `app.user_id` to the target for the lookup and restores the actor's id afterwards. This is the same "act for the account" use of the D-11 policy that `login` and `complete_password_reset` already make. #### Other judgment calls that need a yes or a correction
1. **Password change ends the current session too** (the brief says "all"; F02 kept the caller's own). `POST /api/auth/password/change` returns 204 and clears the cookie; the user signs in again.
2. **Activation flow shape**: `POST /api/auth/activate {token, new_password}` sets the password, consumes the token, ends all sessions. If the user has a `firm_membership` and no TOTP enrolled, the response sets a cookie for a session whose only reachable routes are `/session/me`, `/auth/totp/enrol`, `/auth/totp/enrol/confirm`, `/auth/logout` (the F02 `enrol_required` gate, now reachable only this way); confirm returns the recovery codes and rotates the session to verified, as in F02. Otherwise the response is `{"next": "login"}` and the user signs in. Abandoning the flow leaves a firm user with a password and no TOTP: login refuses generically, the admin issues a new link. The existing `password_reset_*` columns are reused unrenamed; the setting becomes `ACTIVATION_LINK_TTL_HOURS` (default 72) replacing `PASSWORD_RESET_TTL_HOURS`. `POST /api/auth/password/reset` and the `password` field on `POST /api/admin/users` are removed (D-16).
3. **`POST /api/admin/tenants {name, slug}`** (firm_admin, audited to `firm_audit_log` as `tenant_created`): the acceptance criterion "that admin can then create a tenant" needs it; F02 created tenants only from the CLI. No new table.
4. **Firm-membership routes**: `GET/POST /api/admin/firm-memberships`, `PUT/DELETE /api/admin/firm-memberships/{user_id}`; the firm is the actor's own (D-17). Audit events `firm_membership_created / _role_changed / _removed` with `firm_id` set.
5. **Throttle mechanics**: failures counted from `firm_audit_log` rows with `action = 'login_failure'` (steps `password`, `totp`, `recovery`, and the new `link`) and the request's IP in the last `IP_THROTTLE_MINUTES` (15). On the attempt after the 20th (`IP_THROTTLE_FAILURES`), one `ip_throttled` row is written and 429 returned; while an `ip_throttled` row for that IP is inside the window, every attempt returns 429 and writes nothing. Failed link redemption becomes a persisted `login_failure` (step `link`, `firm_id` null) instead of a rollback so it counts. New index `ix_firm_audit_log_ip_occurred_at` in `0003` (an index, not a table).
6. **Client IP**: `TRUSTED_PROXY_COUNT` (default 0). With N > 0 the IP is the N-th from the right of `X-Forwarded-For`; otherwise the socket address. In tests each `TestClient` gets its own socket address so throttle buckets do not collide across tests; the F02 assertion `ip == "testclient"` changes accordingly.
7. **Log-capture assertion for the attempted address**: checked against application log records, not SQLAlchemy's parameter echo, in the same way F02 treats six-digit codes. The lookup `SELECT … WHERE email = :e` necessarily sends the address as a bound parameter, and the harness logs parameters on purpose.
8. **Settings**: `DATABASE_URL`, `CRYPTO_KEYS`, `CRYPTO_ACTIVE_KEY_ID` become required. `DATABASE_OWNER_URL` becomes optional with no default and is required by `alembic/env.py` only, so the API process never has to hold the owner password. A missing variable makes `create_app()` exit with `missing required environment variable(s): …` (names only). The env file path becomes configurable (`ENV_FILE`, default repo-root `.env`) so the start-up test can run without the developer's `.env` and a deployment can point elsewhere.
9. **Dev key material**: `.env.example` carries the dev key `dev1`, so that key is effectively published. I will add a fresh `dev2` key to the local `.env`, make it active, keep `dev1` in the ring so existing local TOTP rows still decrypt (the documented rotation), and strip the key from `.env.example`. No history exists to rewrite here (see Discovered).
10. **CORS**: no CORS middleware is added. The existing middleware additionally refuses, with 403 and no `Access-Control-*` headers, any preflight (`OPTIONS` with `Origin` and `Access-Control-Request-Method`) and any state-changing request whose `Origin` is present and differs from `APP_BASE_URL`. Requests without `Origin` (curl, the CLI) keep working under the CSRF header rule; the Vite proxy passes `Origin: http://localhost:5173`, which equals `APP_BASE_URL`.
11. **CLI**: `scripts/create_user.py` keeps its name and gains subcommands: `bootstrap` (firm + first `firm_admin`, prints the activation link, no tenant needed), `create-user` (optional `--firm-role`, `--membership SLUG:ROLE`, `--entry SLUG`), `issue-link`, `reset-totp` (clears and prints a new link). `--password-stdin` and `--reset-password` go away: D-16 says accounts activate only through a link.
12. **Frontend**: the only change is `ResetPassword.jsx` → `Activate.jsx` calling `/api/auth/activate` and, when told `next: "totp_enrol"`, loading `/` so the existing `TotpEnrol` screen takes over. No admin UI exists, so "admin creates a user → link" in the owner's browser pass is done with `curl` per OPERATIONS.md unless you want a small admin screen (out of the written scope; say so and I will add it).
