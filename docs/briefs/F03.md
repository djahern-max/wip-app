# current-feature.md

## F03 · Ingestion framework
**Roadmap phase**: A · **Blueprint refs**: §3 (principles 4, 7, 8, 10), §6.1, §7 (Integration), §11 (Secrets), §12 · **Decisions**: D-19, D-20, D-21
**Status**: built (2026-09-17), 338 tests (231 + 107); owner browser pass pending (last acceptance criterion, not ticked by Claude Code). Owner answers to the three plan calls recorded below.

### Goal
Everything that enters the platform, a file today and API payloads in F05, is stored as received before anything reads it, can be traced from any later row back to its source, and can be re-submitted without creating duplicates. Background work runs in a worker that always knows which tenant it is working for. No parser, no QBO call, and no domain table is built here; F05 and F06 plug into this.

### In scope
**Tables** (all tenant-scoped: `tenant_id NOT NULL`, leading index, `enable_tenant_rls`)
- `connection`: one row per tenant per system (`system` is text validated against the source registry, not a Postgres enum). `status`, `last_success_at`, `last_error` (text, never a token or payload), token ciphertext with key id. Unique `(tenant_id, system)`.
- `sync_run`: one row per API pull: `connection_id`, `kind`, `started_at`, `finished_at`, `outcome`, counts, `cursor`, `error`. Created and closed through a small service; nothing calls an API in F03.
- `import_batch`: one row per distinct uploaded file: `source_kind`, `sha256`, `byte_size`, `original_filename`, `content_type`, `object_key`, `uploaded_by`, `uploaded_at`, `status ∈ {received, processing, loaded, loaded_with_issues, failed}`, `rows_loaded`, `rows_rejected`, `error`. Unique `(tenant_id, source_kind, sha256)`.
- `raw_record` (D-20): insert-only. `source`, `entity_type`, `external_id`, `version`, `payload` (JSONB), `payload_sha256`, `is_deleted`, `fetched_at`, and exactly one of `import_batch_id` / `sync_run_id` (CHECK). Unique `(tenant_id, source, entity_type, external_id, version)`. Calls `make_append_only()` and is listed in `APPEND_ONLY_TABLES`.
- `task` (D-19): the worker queue. `kind`, `payload` (JSONB, ids only, never source data), `status ∈ {queued, running, succeeded, failed}`, `attempts`, `max_attempts`, `run_after`, `locked_until`, `locked_by`, `dedupe_key`, `last_error`. Partial unique index on `(tenant_id, kind, dedupe_key)` for non-terminal rows.

**Raw store (D-20)**
- `store_raw(session, tenant_id, source, entity_type, external_id, payload, origin)`: if the latest version for that key has the same `payload_sha256`, nothing is written; otherwise a new row with `version + 1`. A delete from the source is a new version with `is_deleted = true` and the last known payload. Prior versions are never touched.
- `latest_raw(...)` returns the current version per key; a history read returns all versions in order.
- `external_id` is a string the source supplies. A source must supply a deterministic key for rows that arrive without one; how LMN does that is F06's question, not this feature's.
- Money safety (CLAUDE.md Money): the engine's JSON deserializer uses `parse_float=Decimal`, and the serializer writes `Decimal` as a JSON number without passing through `float`. `payload_sha256` is computed over a canonical serialization (sorted keys, no whitespace, Decimals as written).

**Object storage (D-21)**
- `ObjectStore` protocol in `app/core/storage.py`: `put(tenant_id, relative_key, stream)`, `open(tenant_id, relative_key)`, `signed_url(tenant_id, relative_key, ttl)`, `exists(...)`. The store builds the `tenant/{tenant_id}/` prefix itself; callers never pass a full key. Relative keys containing `..`, a leading `/`, or a backslash are refused.
- `LocalObjectStore` for development, tests, and CI (directory from `LOCAL_OBJECT_STORE_DIR`; the default location is gitignored and CI fails if anything under it is tracked). `S3ObjectStore` for DigitalOcean Spaces via `boto3`: private ACL, signed URLs with `SIGNED_URL_TTL_SECONDS` (default 60). Selected by `OBJECT_STORE` in `Settings`; the Spaces credentials have no defaults and are required only when `OBJECT_STORE=s3`.
- Import objects are content-addressed: `imports/{sha256}.{ext}` under the tenant prefix, so a retried upload overwrites the identical object. The original filename is a column, never part of a key.

**Upload and import pipeline**
- Source registry in `app/integrations/base.py`: a source kind declares its name, accepted extensions, and a `parse(stream) -> Iterable[RawItem]` callable. F03 registers one production kind, `unparsed_file` (stores and checksums the file, yields no records), so the pipeline can be exercised end to end before F06. A test-only CSV source lives under `tests/` and is registered by `conftest.py`, the same pattern as `tests/probes.py`.
- `POST /api/imports` (multipart; capability `can_manage_imports` = `firm_admin`, `firm_staff`, `client_admin`): streams to a temporary file while hashing, enforces `MAX_UPLOAD_BYTES` (default 25 MB) and the source kind's extensions, writes the object, then inserts `import_batch`, the `task`, and the `audit_log` row (`import_uploaded`) in one transaction. **Raw before normalized**: the object is written before the row is committed.
- The same bytes for the same tenant and source kind return the existing batch with `duplicate: true`: no second batch, object, or task; one `import_duplicate` audit row.
- `GET /api/imports` (list, newest first), `GET /api/imports/{id}`, `GET /api/imports/{id}/download` (signed URL for S3, streamed for local; audited `import_downloaded`). Same capability. A batch in another tenant is 404.
- Task `import.process_batch(tenant_id, import_batch_id)`: opens the object, runs the source's `parse`, calls `store_raw` per item with `import_batch_id` as origin, sets counts and status. A `parse` that raises marks the batch `failed` with a short error and does not retry forever; an item-level failure is counted in `rows_rejected`, the batch ends `loaded_with_issues`, and the remaining items still load (CLAUDE.md: importers never fail a whole file for bad rows). Row-level `exception` records belong to F06/F09.
- Re-processing a batch is safe: identical payloads write nothing (`store_raw`).

**Worker (D-19)**
- `python -m app.worker`, `make worker`. No Redis, no queue library.
- Poll loop: read the tenant list (global table), then **for each tenant open `tenant_session(engine, tenant_id)` and claim at most one due task with `FOR UPDATE SKIP LOCKED`**; one transaction per tenant, never two tenants in one transaction. `LISTEN/NOTIFY` on one channel whose payload is only a tenant id wakes the loop early; polling remains the fallback (`WORKER_POLL_SECONDS`, default 5).
- Claiming marks the task `running` with a lease (`locked_until`) and commits. The work runs in its own transaction(s) under the same tenant context. Completion is a third short transaction. A lease that expires makes the task claimable again; attempts and exponential backoff via `run_after`; after `max_attempts` the task is `failed`.
- Task functions are registered with a decorator that **refuses any function whose first parameter is not `tenant_id`**. The worker passes it explicitly and sets the context with `tenant_session`. Nothing under `app/worker/` or any task module may reference `Principal`, `active_tenant_id`, or `firm_ids` (static test).
- Worker log lines carry task id, kind, tenant id, attempt, outcome. Never a payload, filename, or token.

**Connection tokens and key rotation**
- `app/core/crypto.py` gains optional associated data. Connection tokens are encrypted with associated data `tenant_id | connection_id | field`, so a ciphertext copied to another row or tenant fails to decrypt. Existing TOTP ciphertexts (no associated data) keep decrypting.
- `set_connection_tokens` / `get_connection_tokens` service functions; audited (`connection_tokens_set`, without values). No OAuth flow, no HTTP client (F05).
- `scripts/reencrypt.py`: re-encrypts TOTP secrets on `user` and connection tokens under the active key, one transaction per tenant for tenant tables, idempotent, prints counts by key id before and after, never prints a value. OPERATIONS.md key-rotation runbook updated to use it.

**Frontend**
- One plain "Imports" page for roles with the capability: choose source kind and file, upload, list of batches with status, counts, uploader, time, and a download control. No request fires from a mount effect other than GETs; `test_frontend_effects.py` must still pass with no new allow-list entry. Submit control disabled while in flight.

**Housekeeping**
- CI and local tooling move from Node 20 to the current LTS; state the version chosen.
- OPERATIONS.md: running the worker, what a stuck or failed task looks like and how to requeue it, object-store settings, the re-encrypt command.

**Dependencies approved for this feature**: backend `boto3`, `python-multipart`. Anything else: stop and ask.

Normalizers and every domain table (`customer`, `job`, `estimate`, `billing`, `ledger_line`, …). The `exception` table and queue (F09). Tenant configuration and `account_map` (F04). **Open questions — proposed answers (awaiting go-ahead)**

1. **Worker lease, heartbeat, attempts, backoff.** Lease `WORKER_LEASE_SECONDS` = 300, **no heartbeat**, `TASK_MAX_ATTEMPTS` = 5, backoff `run_after = now + min(30 s × 2^(attempts−1), 15 min)` → 30 s, 1 min, 2 min, 4 min between the five attempts, no jitter. Reasoning: every F03 task is a bounded file parse (≤ 25 MB) and is idempotent by design (`store_raw` hash check), so the failure mode of a fixed lease — a slow task reclaimed and run a second time — is safe, and a heartbeat would need a second connection per running task and would turn a hung task into one that is never reclaimed. Tasks must finish inside the lease or split their work (F05 sync: one task per CDC page); the runner logs a warning when a task overruns. Five attempts with a 15-minute cap covers a database restart or a Spaces blip without hammering; no jitter because there are one or two workers, not a fleet. An expired lease on a task already at `max_attempts` is marked `failed` by a sweep before the claim.
2. **Engine JSON codec.** `create_app_engine` passes `json_serializer=canonical_json` and `json_deserializer=partial(json.loads, parse_float=Decimal)`; SQLAlchemy's psycopg dialect installs these on every connection through psycopg's `set_json_dumps` / `set_json_loads`, so every JSON/JSONB column (`audit_log.detail`, `firm_audit_log.detail`, the new `payload`, `cursor`, `task.payload`) uses them with no per-column type. `audit_log.detail` keeps working because its values are `str`/`int`/`bool`/`None`/nested dicts, which the canonical encoder writes identically (jsonb discards key order and whitespace anyway) and `parse_float` touches only float literals, which no audit row contains; the one behavioural change is that a `float` in any JSON write is now refused at the engine, which is the money rule enforced rather than assumed. Alembic's engine is separate and unaffected. The harness engines (`owner_engine`, `rw_engine`) will be built through `create_app_engine(url)` so tests read the same way the app does.
3. **`sync_run.cursor`: JSONB.** §6.2 needs two cursor shapes in F05: the backfill position per entity (`{"entity": "Bill", "start_position": 1001}`) and the CDC watermark (`{"changed_since": "2026-09-17T00:00:00Z", "entities": [...]}`), and webhooks add a third (event ids). Text would force F05 to invent an ad-hoc encoding or migrate the column; JSONB holds each shape as-is, is read through the same Decimal-safe codec, and costs nothing now. Nullable (a run that failed before producing a cursor).
