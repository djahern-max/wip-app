## F07.2 · Pick what to work on (tracked customers and projects)
**Roadmap phase**: B · **Blueprint refs**: §3 (principles 2, 3, 6), §5, §10 · **Decisions**: D-22, D-35, D-37 (drafted with this brief)
**Status**: drafted 2026-10-04 by the owner's design partner; built 2026-10-04 (migration 0012; D-37 appended); the owner's pass on `rye-beach` is open (ROADMAP ◐). A patch under F07; it changes no accounting behaviour.

### Goal
The owner picks the QuickBooks customers and projects to work on, one at a time, and the Jobs and Customers screens show those and nothing else. On `rye-beach` today the Jobs page lists several hundred "QuickBooks projects with no job" sentences for old sub-customers and the Customers page opens on a long duplicates list; neither helps a person take one job through. After this patch a fresh tenant shows an empty, quiet Jobs page, the owner searches for a project, ticks it, and makes or links its job. What the sync fetches and holds is untouched, so every total and tie-out reads the same as before (D-37).

### In scope
**Decision**
- Append D-37 to `docs/DECISIONS.md` after the last entry, word for word from the owner's paste (source: project knowledge, `claude/decisions-draft-2026-10-04.md`). The owner confirms the number against the tail of the file first. Nothing earlier is edited.

**Tracked flag**
- A `customer` row can be tracked. Track and untrack are by `customer` id (the QuickBooks id's row), never by name. One audit row per item acted on (`customer_tracked`, `customer_untracked`).
- Linking a `qbo_customer` alias to a job (F07) tracks the row in the same action; the existing `job_alias_linked` audit row records it in its detail. Untrack is refused (409, one sentence) while the row has a job link.
- The QuickBooks sync writer must not clear the flag when it rewrites a customer row.

**Customers page becomes the picker**
- A search box over the tenant's active `customer` rows by name (a read; names reach no write path), paged; projects listed before sub-customers before plain customers. Each row: name, parent, what it is (project / sub-customer / customer), QuickBooks id, counts of invoices and payments, a Track control, and "Job: <name>" with a link when linked.
- Above the search, "Tracked": the tracked rows, each with its job or the sentence that it needs one.
- "Possible duplicate customers" moves behind a link on this page; its content and endpoint are unchanged.

**Review item**
- `LEDGER_PROJECT_NO_JOB` is raised for a tracked row with no job alias, with or without documents, and for no other row (D-37). The Jobs page block "QuickBooks projects with no job" is not drawn when there is none.
- Job link candidates, suggestions and the search on a job's QuickBooks section are unchanged.

**Answers to the five questions**

1. **Where the flag lives: two nullable columns on `customer`, no new table.** `tracked_at timestamptz NULL` and `tracked_by uuid NULL REFERENCES "user"(id)`, with a CHECK keeping them both null or both set (the 0011 `kind` pattern). NULL means not tracked, so no existing row is rewritten by the schema step and there is no default to argue about. A new table (`tracked_customer`) was the alternative; it would need its own RLS, a seed in `test_rls.py`, an append-only decision and a join on every read, for one boolean per row. `customer` already has `tenant_id NOT NULL`, RLS enabled and forced, and an index leading with `tenant_id`, so the enumeration tests are unaffected and no helper call is needed. No new index: a tenant's tracked rows are a handful among a few thousand, and RLS already narrows every read to the tenant. **One data step** (see 5): for every `job_alias` with `system = qbo_customer`, set the row's `tracked_at = linked_at` and `tracked_by = linked_by` where still null, with `SET LOCAL app.tenant_id` per tenant as CLAUDE.md requires, so what the owner has already linked on `rye-beach` is tracked on deploy. **Amendment 1 (owner, 2026-10-04)**: `tracked_by` is the user who made the link, read from `job_alias.linked_by` (set by `link_alias` from `actor.user_id`; `linked_at` is the row's own timestamp), so the row says who and when exactly as the link did. **The data step writes no audit row.** A migration writes nothing a person did not do; the person's action was the link, and its `job_alias_linked` row in `audit_log` (entity `job`, `after.display_name` and `rows.job_alias` naming the QuickBooks id) is the record. D-37 says the link tracks the row, so that row is the record of the tracking too; from 0012 on, `link_alias` also writes `customer.tracked_at` before and after into the same row. Reversible: the downgrade drops the CHECK, the FK and the two columns; who tracked what stays in `audit_log`; the guard refuses `wip`.
2. **Keeping the sync writer off the flag: nothing to change in `sync.py`, one test to prove it.** `_apply_customer` loads the existing ORM row and assigns `display_name`, `parent_external_id`, `parent_customer_id`, `is_project`, `active` and `raw_record_id` by name; it never builds a replacement row, bulk-upserts or deletes a customer, and the follow-up `update(Customer)` sets `parent_customer_id` only. Columns it does not name are not touched. The test tracks a row, applies a renamed raw payload for the same QuickBooks id, and asserts the name changed and `tracked_at`/`tracked_by` did not. **Amendment 2 (owner, 2026-10-04)**: a tracked row that QuickBooks makes inactive **stays tracked** (the flag is a person's decision), is listed under Tracked with "Inactive in QuickBooks" in words, and **raises no `LEDGER_PROJECT_NO_JOB`** (tested); the picker's search shows active rows only, as the brief says, and tracking an inactive row by id is refused in one sentence. A QuickBooks merge is unchanged by this patch (Discovered, carried: still to be checked in the sandbox).
3. **Endpoint shapes and paging.** All on the existing `customers_router` (`/api/customers`), guarded by `can_track_customers` (4):
   - `GET /api/customers?q=<text>&page=<n>`: the picker's search. An empty or whitespace `q` returns no rows and the page says "Type part of a name" (the picker stays quiet; **amendment 3**: kept as proposed). Otherwise one SQL query over the tenant's active QuickBooks rows, `display_name ILIKE %q%` with a bound parameter (a read; the name reaches no write path), ordered projects, then sub-customers, then customers, then name, then id; 50 rows a page with `page`, `pages` and `total` in the response (the brief's "paged"; `rye-beach` has several thousand rows, so today's load-everything `customer_rows` is not used here). Each row: `customer_id`, `external_id`, `display_name`, `parent_name`, `kind_label` (Project / Sub-customer / Customer), `billing_count`, `payment_count`, `tracked`, and `job` (`{id, name}` or null).
   - `GET /api/customers/tracked`: every tracked row (active or not), same row shape plus `active`, ordered the same way; the frontend prints "Job: <name>" with a link or the sentence from `LEDGER_PROJECT_NO_JOB`.
   - `POST /api/customers/{customer_id}/track` and `POST /api/customers/{customer_id}/untrack`: no body; the id is the `customer.id` (the QuickBooks id's row, as `link_alias` resolves it). 404 in one sentence for a row not in the tenant's copy; 409 in one sentence for track on a tracked row or untrack on an untracked one (nothing happens, so nothing is audited; one audit row per item acted on); 409 for untrack while a `job_alias` points at the row ("…is linked to job X; unlink it there first."). Each success writes one audit row, `entity_type = customer`, `entity_id` = the row, `after`/`before` carrying `external_id`, `display_name`, `tracked_at`, `tracked_by`.
   - `GET /api/customers/duplicates`: unchanged, same guard as today.
   - The job's own `qbo-candidates` and `qbo-search` are unchanged (owner's answer 21 stands: unaliased active rows, 25 results).
4. **Roles.** Linking a job today is `can_manage_jobs` = `firm_admin`, `firm_staff`, `client_admin` (`FIRM_AND_CLIENT_ADMIN`); viewing jobs is every role; the duplicates list is `can_view_customer_duplicates` = the same three. Track, untrack, the search and the Tracked list get their own guard, `can_track_customers = require_roles(*FIRM_AND_CLIENT_ADMIN)`, registered in `CAPABILITIES` as `track_customers` so `tests/probes.py` mounts it and `tests/test_roles.py` asserts the cell for each of the five roles (`client_pm` and `client_viewer` refused). The Shell already shows "Customers" to `canManageJobs` only; it stays that way.
5. **Stored, not derived.** The flag is a column (1), set by the picker and by `link_alias` (when null: `tracked_at = now`, `tracked_by = actor`, recorded in the `job_alias_linked` row's `rows` as `customer.tracked: [null, at]`), and never cleared by `unlink_alias`; untrack reads `job_alias` and refuses while a link exists. Deriving ("tracked = picked or aliased") would still need the picked flag and would make one word read from two places; the stored flag means `LEDGER_PROJECT_NO_JOB`, the Tracked list and the picker all read one column. The invariant "every row with a QuickBooks link is tracked" is kept true by `link_alias`, by the migration's data step for links made before 0012, and by one test that links, unlinks and checks the flag each way.
