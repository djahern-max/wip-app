### Goal
Every estimate the platform will ever need is in the spine as a row it can match by external id, loaded from the platform's own estimate template (D-32): the estimate's id, estimator, client, jobsite, name, status, price and date from the *Estimates* sheet; its work areas from the *Work areas* sheet (order number, name, kept or omitted, price, notes); and, under each work area, its **cost lines** from the *Estimate costs* sheet (cost code, hours, amount), so that estimated cost by cost category and EAC in the D-04 basis come from the same codes the ledger uses (D-23). Re-uploading the same file changes nothing; a newer file updates by id and keeps every earlier version, so a work area that appears or disappears after the baseline is visible as a change (D-01). Dirty rows never stop a file: the row loads if it can and raises a named exception if it cannot. Nothing here touches a job, a customer, or QuickBooks: linking an estimate to a job is F07. No parser is written for any estimating system's own report or paste (D-32).

### In scope
**Source (`EstimateSource.parse(file) -> list[EstimateDTO]`, BLUEPRINT §6.3, on the F03 `parse` protocol; one registered `SourceKind` with a D-22 label)**
- **Estimate template** (`estimate_template`, label "Estimate template"): one workbook (`.xlsx`) with sheets *Estimates*, *Work areas* and *Estimate costs* found by name (a *Read me* sheet is ignored), or one `.csv` per sheet recognised by its column header. Columns: Estimates `estimate_id, estimator, client, jobsite, name, status, price, estimate_date`; Work areas `estimate_id, order, kept, name, price, notes`; Estimate costs `estimate_id, order, cost_code, hours, amount, notes`. One workbook may carry any number of estimates. `kept` is `Y` or `N`; anything else rejects the row with a sentence. `status` is Pending, Sold or Lost; any other word loads with `status_norm` null and raises `EST_UNKNOWN_STATUS`. A work-area or cost row whose `estimate_id` is neither on the file's Estimates sheet nor already in the spine is rejected with a sentence. No upload parameter: the estimate id is a column. The blank template with its Read me, `docs/templates/estimate_template.xlsx`, is generated by a script and linked from OPERATIONS.md.
- The `lmn_closing_report`, `lmn_work_areas` and `estimate_csv` kinds of the first draft are **not built** (D-32).

**Tables (BLUEPRINT §7 Spine; D-01 adds `estimate_work_area`; D-32 keys `estimate_cost` to the work area; all with `tenant_id`, `enable_tenant_rls`, migration `0010`)**
- `estimate`: `external_id` (unique per tenant and source), `source`, `estimator`, `client_name`, `jobsite`, `name`, `status` as received and `status_norm` (`pending`, `sold`, `lost`, or null for an unknown word), `price` (the control total), `estimate_date` (DATE, nullable; the owner's answer of 2026-09-25 replaces the first draft's report-date columns). Client and jobsite are text on the estimate; no link to `customer` (F07).
- `estimate_version`: one row per accepted upload that touched the estimate, `import_batch_id`, `received_at`, `kept_total`, `is_baseline` (the first work-areas version received while `status_norm = sold`, D-01 as answered; see Behaviour).
- `estimate_work_area`: per version: `order_no`, `name`, `kept`, `change_order_suggested` (from the name: "CO:", "C/O", "CO " prefix; a suggestion for F07, never a decision), `price`, `notes`. Work-area identity across versions is `order_no`, the same key D-26 puts on invoice lines. A work area's cost is the sum of its cost lines, computed, never stored.
- `estimate_cost(tenant_id, estimate_work_area_id, cost_category_id, division_id, cost_code, hours, amount)`: one row per cost line; unique `(tenant_id, estimate_work_area_id, cost_category_id)`; `ondelete=RESTRICT`. The cost code on the sheet resolves to `(division, cost_category)` through the F04 grid (`division.code_digit` + `cost_category.slot`); `division_id` is stored for the tie-out; a code not in the grid is stored as text with null category and division and raises `EST_UNKNOWN_COST_CODE`.
- Every money column `NUMERIC(14,2)`; every value parsed as `Decimal` (`Decimal(repr(cell))` for a numeric cell) and quantized `ROUND_HALF_UP` to the cent at parse, the one defined rounding point in this feature. Hours are `NUMERIC(9,2)`.

**Behaviour**
- Idempotent by external id (§6.1): the same file again is a no-op and the batch says "Nothing changed: this file was already loaded."; a newer file updates status, price and header fields by id and records a new version; an estimate absent from a newer file is left as it was.
- Control total: the kept work-area prices of a version must equal the estimate's price; a difference raises `EST_PRICE_MISMATCH` with both amounts and the version still loads.
- Cost lines: a kept work area priced above 0.00 with no cost line leaves a sold estimate under `EST_NO_CATEGORY_SPLIT` (D-04) until a person supplies the lines; an omitted or 0.00 work area needs none, and a cost line under one is loaded, left out of every total and reported as `EST_COST_LINE_ON_OMITTED`. Cost by category = the sum of cost lines over kept work areas; EAC in the D-04 basis = that sum less the slots the tenant's `wip_basis` policy excludes.
- Baseline and version comparison (D-01, owner's answer to question 11): the baseline is the first work-areas version received while the estimate is sold. Versions received while pending, lost or unknown carry `is_baseline = false` and raise no comparison exceptions; when a later upload marks the estimate sold, the latest work-areas version at that moment becomes the baseline. A later work-areas version is compared to the baseline by `order_no`: a kept work area not in the baseline is a change order by definition (flag set, no name needed); a baseline original work area now omitted raises `EST_DEDUCTIVE_CHANGE` with the order number and price; a kept work area whose name at an order number differs from the baseline raises `EST_WORK_AREA_RENUMBERED` rather than being re-keyed.
- Exceptions, each a code plus one plain sentence (§10; the `exception` table is F09, so these are recorded as answered under Plan question 5 and F09 adopts them): `EST_NO_ID` (a row with no `estimate_id`: not loaded, the batch issue carries the row), `EST_ZERO_SOLD` (0.00 price on a Sold estimate only), `EST_UNIT_PRICED` (a work-area name that reads as a rate: "per Day", "per Hour", "per Load"; D-24, a suggestion for F07 to resolve), `EST_NO_CATEGORY_SPLIT` (D-04), `EST_PRICE_MISMATCH`, `EST_DEDUCTIVE_CHANGE`, `EST_WORK_AREA_RENUMBERED`, `EST_UNKNOWN_COST_CODE`, `EST_COST_LINE_ON_OMITTED`, `EST_UNKNOWN_STATUS`. Pending and lost estimates at 0.00 load silently. An unpriced change-order work area (0.00, D-26 "#26" case) loads kept with no exception; F08.1 raises on the instruction, not the row.
- Audit: `estimate_created`, `estimate_updated` (id, changed fields, version), `estimate_version_created`, one row per estimate, never one per file.
- Roles: upload by `firm_admin`, `firm_staff`, `client_admin`; read by every role; the role matrix test extended.

**Design**

*Parsing (`app/integrations/estimate_template.py`, shared `app/integrations/cells.py`)*
- Cells to `Decimal` in one helper: `int` → `Decimal(int)`; `float` → `Decimal(repr(value))` (the exact shortest form of what the workbook stores, as F04's `_cell_text`); text → commas, `$` and spaces stripped, then `Decimal(text)`; anything else is unreadable. Money is quantized `ROUND_HALF_UP` to cents in that helper, the one rounding point of this feature; hours the same way to two places. The F03 hygiene scan already covers `app/integrations/`.
- Workbook: sheets found by name (trimmed, case-folded: `estimates`, `work areas`, `estimate costs`); any other sheet ignored; a workbook with none of the three is a batch that reads nothing (`nothing_loaded`). CSV: the header row decides which sheet it is (`estimate_id, estimator, …` / `estimate_id, order, kept, …` / `estimate_id, order, cost_code, …`); a header matching none fails the parse. Columns are located by header name on every sheet (the template's headers are the contract); a missing required column fails the parse with the F03 sentence; extra columns are ignored. Row rules: `estimate_id` trimmed, upper-cased, `^EST\d+$`, else `RejectedItem(code="EST_NO_ID", detail=the row's cells)` when empty, or a plain rejection when malformed; `status` as received, `status_norm` from the case-folded word; `kept` Y/N only; `order` an integer; `price`, `amount`, `hours` through the helper; `cost_code` as text (digits expected, not enforced at parse); duplicate `(estimate_id, order)` on Work areas rejects the second row; a Work areas or Estimate costs row for an `estimate_id` that is neither on the file's Estimates sheet nor in the spine is rejected (the parser cannot see the spine, so the parser yields the rows and the normalizer rejects them into `import_batch.issues`, see below).
- Raw records (`source = "template"`): per estimate id in the file, entity `estimate` (the Estimates row, when present) and entity `estimate_detail` (the file's work areas for that id, each with its cost lines nested by order; when present). A cost line whose `order` has no work area in the same file is a rejected row (a sentence, no `EST_*` code). One `RawItem` per entity per estimate, so an identical re-export writes nothing (D-20) and a changed one is a new raw version.
- Name rules, one constant each in `app/domain/estimates/names.py` (question 8): `CHANGE_ORDER_PREFIX = r"^\s*(?:CO:|C/O\b|CO\s)"` (case-insensitive) and `UNIT_PRICE_WORDS = r"\bper\s+(?:day|hour|hr|load)\b"` (case-insensitive). Tests: 67 Elm rows 18–21 flagged and 1–17 not; Turley rows 23–32 flagged; only 67 Elm row 18 unit-priced.

*Pipeline (F03; two small changes, no protocol change)*
- `RejectedItem` gains `code`, `message`, `detail` (JSON, small: ids, order numbers and amounts as strings; the row's cells for `EST_NO_ID`); the pipeline collects them into `import_batch.issues JSONB` (a list) in the batch's final transaction beside `rows_rejected`; the normalizer may append to the same list. `ImportBatchOut.issues` returns them and the Imports page lists them under the batch, one sentence each.
- `FOLLOWUP_OUTCOMES` gains `unchanged`; the follow-up sentence reads "Nothing changed: this file was already loaded." (`after_load_subject` "estimates").

*Normalizer (`app/domain/estimates/normalize.py`, task `estimates.normalize`, chained by `after_load` like `config.normalize_chart`)*
- Per estimate id in the batch, in one transaction per batch: the `estimate` record creates the estimate (`estimate_created`) or, when its raw version is new to the spine, updates the header fields (`estimate_updated` with the changed fields); the `estimate_detail` record, when its raw version is new, makes one `estimate_version` with its `estimate_work_area` rows (full snapshot per version; identity `order_no`) and their `estimate_cost` rows; one `estimate_version` per estimate per batch whenever anything of that estimate changed (`kind = detail` when it carries work areas, else `header`), `estimate_version_created` once. A detail record for an id with no estimate in the spine and no Estimates row in the file is rejected into `import_batch.issues` with a sentence and not loaded. A batch where nothing changed ends `unchanged`.
- Cost-code resolution at write: `cost_code` text → division by its first character (`division.code_digit`) and category by its last two (`cost_category.slot`), both active for the tenant; unresolved → `cost_category_id` and `division_id` null, text kept.
- Baseline: on creating a detail version while `status_norm = sold` and no baseline exists, mark it; on a header change to sold with no baseline, mark the latest detail version if any. Comparison (pure, `app/domain/estimates/versions.py`) runs only when a baseline exists and the new version is not it: (a) kept and not in the baseline → `change_order_suggested = true`; (b) baseline original, now omitted → `EST_DEDUCTIVE_CHANGE` (order, price); (c) kept, same order, different name (trimmed, case-folded) → `EST_WORK_AREA_RENUMBERED`, nothing re-keyed. The flag from (a) is stored on the row; (b) and (c) are derived at read time from the baseline and the latest version.
- Idempotent and re-runnable: a re-run finds every raw version applied and reports `unchanged`. Nothing is ever removed because it is absent from a file.

*Tables (migration 0010; `enable_tenant_rls` on all four; every FK `ondelete=RESTRICT`)*
- `estimate`: `id`, `tenant_id`, `source` (`template`), `external_id` (unique per tenant and source), `estimator`, `client_name`, `jobsite`, `name`, `status`, `status_norm` (pending | sold | lost | NULL, CHECK), `price` NUMERIC(14,2) NOT NULL, `estimate_date` DATE nullable, `latest_version_id` FK nullable, `created_at`, `updated_at`. Indexes `(tenant_id, status_norm)`, `(tenant_id, estimator)`.
