## F05 · QBO connection & sync (sandbox)
**Roadmap phase**: B · **Blueprint refs**: §3 (principles 1, 4, 7), §6.1, §6.2, §7 (Integration, Billing), §11 (Secrets, Audit), §13.7 · **Decisions**: D-19, D-20, D-22, D-25
**Status**: closed 2026-09-21 (owner pass on the live sandbox, 2026-09-21; 533 backend + 12 frontend tests).

### Goal
A firm admin connects a tenant to a QuickBooks Online company, and from then on the platform holds an exact, traceable, read-only copy of that company's customers, projects, accounts and sales-side transactions, kept current by change polling. Every payload is stored as received before anything reads it. Monthly billed and collected totals in the platform equal QuickBooks' own reports. This feature is built and accepted against the Intuit **sandbox** company only (D-25); the production connection to Rye Beach and webhooks are F05.1. The platform never writes to QuickBooks.

**Connection (OAuth2)**
- Settings, no defaults, required only when a QBO route or task runs: `QBO_CLIENT_ID`, `QBO_CLIENT_SECRET`, `QBO_ENVIRONMENT` (`sandbox` | `production`; selects the API base URL), `QBO_REDIRECT_URI` (development: `http://localhost:5173/api/qbo/callback`, through the Vite proxy). The secret is never logged, returned, or written to the database.
- `POST /api/qbo/connect` returns the Intuit authorization URL with scope `com.intuit.quickbooks.accounting` only. `state` is single-use, expires in 10 minutes, is bound to the tenant and the user who started it, and is stored hashed. `GET /api/qbo/callback` validates `state`, exchanges the code, stores tokens through `set_connection_tokens` (encrypted with associated data, F03), records `realm_id`, then redirects to the Connections page. A callback with an unknown, used or expired `state` changes nothing and says so in one plain sentence. The plan must state how the callback works if the session cookie is not sent on the redirect from Intuit.
- One QuickBooks company per tenant (`connection` unique on `(tenant_id, system)`). Connecting a company whose `realm_id` is already connected to another tenant is refused.
- Refresh: before a call when the access token is near expiry, and on a 401 once. **Every token response replaces both stored tokens** (Intuit rotates the refresh token); expiry times are read from the response, not assumed. Two workers refreshing at once must not lose the newer token (row lock; test it).
- Refresh failure (`invalid_grant`), or a revoked connection: `connection.status = needs_reconnect`, audited, shown on the Connections page with a "Reconnect" action; tasks for that connection stop retrying and do not crash. The `exception` table does not exist until F09; F09 will raise its exception from this status.
- Disconnect: revoke at Intuit, clear tokens, status `disconnected`, audited. Synced data stays.
- Capability `can_manage_connections`: `firm_admin` only. Read of connection status: `firm_admin`, `firm_staff`, `client_admin`. `client_pm`, `client_viewer`: 403.
- Audit (same transaction): `connection_started`, `connection_completed`, `connection_tokens_set` (exists), `connection_needs_reconnect`, `connection_disconnected`, `sync_requested`. Never a token, code, or `state` value in `detail`.

**HTTP client**
- One module, `app/integrations/qbo/client.py`; core Accounting REST API only, the Projects GraphQL API is not used. `minorversion` pinned in one constant (propose the value; 75 or later). Timeouts set. 429 and 5xx: backoff, honouring `Retry-After`; at most one request in flight per connection.
- **Response bodies are parsed with `app.core.jsoncodec.json_loads`, never `response.json()`**: QuickBooks sends amounts as JSON numbers and no amount may pass through `float`. Hygiene test extended to `app/integrations/qbo/`.
- Log lines carry entity, count, status code and Intuit's `intuit_tid`; never a payload, token, or customer name.

**Backfill and change polling**
- Entities stored raw, all of §6.2: Account, Customer, Vendor, Item, Invoice, Payment, CreditMemo, SalesReceipt, Deposit, Bill, VendorCredit, Purchase, JournalEntry, TimeActivity, Preferences, CompanyInfo. Cost-side entities are stored raw now so F10 needs no new API work; **F05 normalizes none of them**.
- Backfill by entity with query paging; **one task per page** (lease is 300 s, no heartbeat). Each page goes through `store_raw` with a `sync_run` as origin, then the normalizer for that entity is enqueued. Raw before normalized.
- Change Data Capture polling per connection every `QBO_CDC_POLL_MINUTES` (default 15), using the last successful cursor. A delete reported by CDC is a new raw version with `is_deleted` (D-20). If the cursor is older than Intuit's CDC look-back window, the connection page says a fresh backfill is needed and offers it; it never happens silently on a schedule. The plan states how the recurring poll is scheduled with the existing queue (`run_after`, `dedupe_key`); no scheduler dependency.
- "Sync now" on the Connections page enqueues one CDC poll.
- Nightly drift check per connection: entity counts from QuickBooks (`SELECT COUNT(*)`) against current non-deleted raw records, and month totals of normalized billing and payments against a re-sum of raw. A difference sets `sync_run.outcome = drift` with the entity and the two numbers, shown on the Connections page. No full re-pull.

**Tables** (new; all tenant-scoped: `tenant_id NOT NULL`, leading index, `enable_tenant_rls`; money `NUMERIC(14,2)`; accounting dates `date`)
- `customer`: `source`, `external_id` (QBO Id), `display_name`, `parent_external_id`, `parent_customer_id`, `is_project`, `active`, `raw_record_id`. Unique `(tenant_id, source, external_id)`. A project is a customer row with `is_project = true` and a parent. Names are data; nothing matches on them.
- `billing`: `kind ∈ {invoice, credit_memo, sales_receipt}`, `source`, `external_id`, `doc_number`, `txn_date`, `due_date`, `customer_id`, `subtotal`, `tax_total`, `total`, `balance`, `voided`, `deleted_at`, `raw_record_id`. Unique `(tenant_id, source, kind, external_id)`. Amounts are stored positive as QuickBooks gives them; one function returns the signed amount (credit memos negative). Which of `subtotal` or `total` feeds **billed to date** is decided in F08, not here.
- `billing_line`: `billing_id`, `line_no`, `external_line_id`, `description`, `item_external_id`, `amount`.
- `payment`: `source`, `external_id`, `txn_date`, `customer_id`, `total`, `unapplied_amount`, `deposit_account_external_id`, `deleted_at`, `raw_record_id`.
- `payment_application`: `payment_id`, `linked_txn_type`, `linked_txn_external_id`, `billing_id` (nullable: set when the linked transaction is a `billing` row we hold), `amount`.
- `connection` gains `realm_id`, `environment`, token expiry timestamps, company name, and the pending-`state` columns. `gl_account` gains no column: QBO `Account.Id` is attached to `external_id` by **account number** (`AcctNum`), an identifier. An Account with no `AcctNum` is stored raw, counted on the Connections page as "accounts without a number", and creates no `gl_account` row.

**Normalizers** (pure functions from the latest raw version to canonical rows; idempotent; re-runnable; tests first)
- Customer → `customer`. Invoice, CreditMemo, SalesReceipt → `billing` + `billing_line`. Payment → `payment` + `payment_application` from its `LinkedTxn`.
- SalesReceipt is billed and collected in one document: it produces a `billing` row **and** a `payment` row fully applied to it, both from the same raw record, so collected totals tie. (Owner-confirmed before coding; see Plan.)
- A deleted source record sets `deleted_at`; deleted and voided rows are excluded from every total and remain visible in history. A void is recognised as S-01 finding (d) says.
- **Deposit is stored raw and not normalized in F05.** A QuickBooks deposit line that is not linked to a payment is money received without an invoice; how that is treated is the owner's decision (with D-02) before F08. The Connections page shows how many such lines exist and their total.
- A payload the normalizer cannot read is skipped and counted per entity on the Connections page; the rest of the page still loads (importers never fail a whole batch for bad rows).

**Frontend** (D-22; `.table-wrap` pattern as fixed at the end of F04)
- "Connections" page: status in words, company name, environment, last successful sync, per-entity counts, items needing attention (needs reconnect, drift, skipped payloads, accounts without a number, unlinked deposit lines), and a **month totals** table: Invoices, Credit memos, Sales receipts, Payments, by calendar month of `txn_date`, money as strings with cents, negatives in parentheses. One primary action: "Connect to QuickBooks", or "Sync now" once connected; "Reconnect" and "Disconnect" are secondary. No request fires from a mount effect other than GETs.

**Tenant for the sandbox**: a dedicated tenant (slug `qbo-sandbox`), created through the admin endpoints. The sandbox is never connected to `rye-beach`.

**Fixtures**: recorded sandbox responses under `backend/tests/fixtures/qbo_sandbox/` (Intuit's fictitious sample company), with `realm_id` replaced and no token, code or header. Tests run against these through a stubbed transport; CI never calls Intuit.

**Dependencies approved for this feature**: `httpx` as a runtime dependency (already a dev dependency, D-14). No Intuit SDK, no OAuth library, no scheduler. Anything else: stop and ask.

**Docs**: OPERATIONS.md gains "QuickBooks connection": the four settings, the redirect URI, connect and reconnect, what `needs_reconnect` and `drift` mean and what to do, how to request a fresh backfill, how to rotate the client secret.

#### Design notes the questions depend on
- **Realm uniqueness under RLS.** The app role cannot see another tenant's `connection` rows, so "already connected elsewhere" cannot be a query. A partial unique index on `(system, realm_id)` is enforced by Postgres regardless of RLS; the callback catches the unique violation and answers "This QuickBooks company is already connected to another client." It names no tenant. The tenant-leading index and `tenant_isolation` policy are untouched; no new policy. A disconnected connection keeps its `realm_id` (its data stays, so the company stays claimed).
- **`realmId` on the callback is not trusted.** After the code exchange the client reads `CompanyInfo` for that realm with the new token; Intuit refuses a token for a different realm. That call also supplies the company name.
- **Access log.** uvicorn's access log prints the query string, which on the callback holds `code` and `state`. A logging filter installed in `create_app` rewrites the callback's log record to the path alone; the log-leak scan registers both values so a regression fails the suite.
- **Refresh.** Its own short transaction: `SELECT … FOR UPDATE` on the connection row, re-read expiry (a worker that waited finds the new pair and skips the call), call Intuit's token endpoint, store both tokens and both expiries from the response, commit. It never shares a transaction with an API call, so a later failure cannot roll back a token Intuit has already rotated.
- **One request in flight per connection.** A transaction-level advisory lock keyed on the connection id, taken around each HTTP request in a session of its own. Sequential calls stay far under Intuit's per-minute limit, so no extra pacing.
- **Backfill.** `changedSince` watermark is taken **before** page 1, so anything changed during the backfill is picked up by the first CDC poll. Pages are `ORDERBY Id STARTPOSITION n MAXRESULTS 1000`; each page task stores raw, enqueues the normalizer for that entity, then enqueues the next page (dedupe key `backfill:{sync_run_id}:{entity}:{start}`); an empty page ends the entity. Name-list entities (Customer, Account, Vendor, Item) are queried with `Active IN (true, false)`; QuickBooks hides inactive ones otherwise and the drift counts would never agree. Customers are backfilled before transactions.
- **Order independence.** A payment normalized before its invoice stores `billing_id` NULL; normalizing a `billing` row fills `billing_id` on applications already pointing at its external id. Same for `parent_customer_id`. Both orders give identical rows.
- **Skipped payloads are derived, not stored**: the count per entity is "latest raw versions of a normalized entity that no canonical row points to". `raw_record` stays insert-only and no counter can go stale.
- **S-01 extras I will record while there** (structure only): how a payment line that applies a **credit memo** appears (if both the invoice line and the credit memo line carry positive amounts, criterion 10's identity needs the credit memo line signed negative; I will report, not assume); which of the 16 entities CDC accepts; whether `Id > 'n'` works in a query (keyset paging would be sturdier than `STARTPOSITION`).

#### 1. The callback without a session cookie
The session cookie is `SameSite=Lax`, and Intuit's redirect is a top-level GET navigation, so browsers do send it. It is still absent in ordinary cases: the admin signed in at `127.0.0.1:5173` while the redirect URI says `localhost:5173`, the session idled out on Intuit's consent screen, or a browser with stricter defaults. So the callback **never takes tenant or user from the session**:
- `state` = base64url(16 bytes of tenant id ‖ 32 random bytes). `connect` stores only its SHA-256 on the tenant's `connection` row with the starting user's id and the expiry, replacing any earlier pending `state`. The tenant id has to travel in `state` because `connection` is under forced RLS: without a tenant context the row cannot be found at all, and a table outside RLS to hold pending states would need a decision. A tenant id is an opaque identifier, not a secret; a forged one finds no matching hash.
- The callback parses the tenant id, sets `app.tenant_id`, and claims the state in one statement: `UPDATE connection SET oauth_state_sha256 = NULL … WHERE oauth_state_sha256 = :hash AND oauth_state_expires_at > now() RETURNING …`. Two simultaneous callbacks cannot both win; unknown, used and expired all match nothing and change nothing.
- The user is `oauth_state_user_id`. Before the code is exchanged the callback re-checks that this user is still active and still `firm_admin` in that tenant. If a session cookie **is** present and belongs to a different user, the callback refuses. Audit rows (`connection_completed`, `connection_tokens_set`) carry the state's user as actor.
- The callback sets no cookie and creates no session. It answers with a 303 to `{APP_BASE_URL}/connections?result=<code>`; the page turns the code into one plain sentence ("That connection link was already used or has expired. Start again from Connect to QuickBooks."). If the admin is no longer signed in, the ordinary login screen comes first. `error=access_denied` from Intuit (the admin pressed Cancel) clears the pending state and says so.
- **Owner's call**: the stricter alternative is to refuse whenever the cookie is absent. I recommend the design above: the `state` value is as strong as the session token and reached only the browser that started the flow, and the strict version fails on the `localhost`/`127.0.0.1` case with no way for the admin to tell why.

#### 2. Scheduling with the existing queue
No scheduler: each run enqueues its successor with `run_after`, keyed by time slot.
- **Why slot keys.** The dedupe index covers `queued` **and** `running` rows, so a running poll that enqueues its successor under the same key is silently refused and the chain would end after one run. Keys therefore carry the slot: `cdc:{connection_id}:{slot start, ISO UTC}` where the slot is `run_after` truncated to `QBO_CDC_POLL_MINUTES`. Any number of enqueues for one slot collapse into one task.
- **Successor first.** `qbo.cdc_poll` enqueues the next slot as its first step, in the transaction that opens the `sync_run`, before any call to Intuit. A poll that later fails, or dies with its lease, cannot break the chain.
- **Seeding.** The chain is seeded when a connection completes or reconnects, and at worker start-up: for each tenant, in its own `tenant_session`, a connected QBO connection with no open poll task gets one. Idempotent through the slot key. No transaction holds two tenants.
- **Stopping.** A poll that finds the connection `needs_reconnect` or `disconnected` ends at once and enqueues nothing. `invalid_grant` mid-task raises `PermanentTaskError("needs_reconnect")`: failed at once, no retries, worker unaffected. Reconnect seeds again, and the poll resumes from `latest_successful_cursor`.
- **"Sync now"** enqueues the same task kind with key `cdc:{connection_id}:now`; pressing it twice is one task. It can coincide with a scheduled poll; the advisory lock keeps their requests one at a time and the raw store's hash check makes the overlap write nothing twice.
- **Cursor.** The new `changedSince` is the poll's own start time minus two minutes of overlap, written only when the run succeeds. If the stored cursor is older than 29 days the poll does not call Intuit: the run ends with outcome `failed`, reason `cursor_too_old`, the chain stops, and the Connections page says a fresh backfill is needed and offers it.
- **Nightly drift check**: same pattern, key `drift:{connection_id}:{date}`, `run_after` the next `QBO_DRIFT_HOUR_UTC` (proposed default 7, about 02:00–03:00 Eastern), successor first, seeded with the poll.
- **Metered reads.** One CDC request covers all entities, so polling costs about 96 reads a day per connection (about 2,900 a month), plus about 14 `COUNT(*)` reads a night. Intuit's Builder tier includes 500,000 metered reads a month.
