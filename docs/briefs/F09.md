### Goal
Today every review sentence is computed when a page is read and then forgotten: nobody can say "I have seen this", hand it to someone, or record why it is acceptable, and the same sentence is computed in more than one place. This feature gives each sentence an identity that lasts: an **exception** a person can assign, annotate and dismiss with a note, which clears by itself when its cause is gone. It adds one page, the queue, where a company's open exceptions are listed, and a count per company for firm users. It changes no figure and no accounting behaviour; the generators stay the pure functions they are, and this feature persists what they return.

### In scope

**The model** (one new tenant-scoped table; `tenant_id NOT NULL`, leading index, `enable_tenant_rls`, RLS enumeration test extended; reversible migration; **waits for a yes**)
- BLUEPRINT §7 names it `exception(type, severity, entity_ref, status, assigned_to, resolution_note)`. One row per exception: its code, its severity (§10), what it is about (a job, an estimate, a QuickBooks customer row, by id), a key that tells two exceptions of one code on one subject apart, its status, who it is assigned to, when it was first and last raised, and when and how it closed.
- Status: `open`, `resolved` (the generators no longer raise it), `dismissed` (a person closed it with a note). Whether a note, an assignment and each change of status are rows of their own or columns with audit rows is Plan question 2.
- The sentence is not stored as the truth: it is produced by the generator each time (D-22), so a corrected wording or a changed amount shows at once. What is stored of the sentence, if anything, is Plan question 3.

**The run**
- One function refreshes a tenant's exceptions: it calls the existing generators, opens an exception for each sentence not yet held, updates "last raised" for those still raised, and marks `resolved` those no longer raised. It is idempotent: a second run with nothing changed writes nothing.
- When it runs is Plan question 1 (after each QuickBooks poll and import through the worker, D-19; after a write that changes a generator's inputs; on a schedule). "Next run" in the roadmap's acceptance means the next of these.
- Generators in scope, as built and unchanged: the estimate set (`app/domain/estimates/exceptions.py`, including the F06.1 burden sentences), the job and link set (`app/domain/jobs/issues.py`: `EST_UNATTACHED`, `JOB_NO_LEDGER_LINK`, `LEDGER_PROJECT_NO_JOB`, `JOB_SECOND_ESTIMATE_FOR_CUSTOMER`, `JOB_DIVISION_UNSET`, `CO_APPROVAL_NOT_CARRIED`), and the billing set (`PAYMENT_UNAPPLIED`, `DEPOSIT_NOT_IDENTIFIED`, `BILLED_OVER_CONTRACT`, `PAYMENT_OTHER_CREDIT`, `BILLING_UNAPPROVED_CO`, `PAYAPP_NOT_INVOICED`, `INVOICE_NO_PAYAPP`, `PAYAPP_INVOICE_MISMATCH`). Each code's severity is §10's; a code §10 does not list gets its row there in this change.
- The sentences are computed once per subject and every page reads that one result (carried: the board's Attention column and Home compute them in two reads; the Estimates list and the estimate detail differ by the burden sentences).

**What a person can do**
- **Assign** an open exception to a member of the company, or to nobody. One audit row.
- **Add a note** to an exception, any number of times; notes are kept in order with who and when.
- **Dismiss** an open exception: a note is required and the request is refused in one sentence without it. One audit row. Which exceptions may be dismissed, and when a dismissed one opens again, are owner questions A and B.
- **Reopen** a dismissed exception. One audit row.
- Nobody resolves an exception by hand: `resolved` is only ever set by the run.
- Roles: owner question C.

**Screens (D-22)**
- **Exceptions** page (a new link in the navigation, with the open count): one table of the company's exceptions, open first, then by severity and age: the sentence, what it is about (a link to the job, estimate or Customers page), severity in words, first raised, assigned to, status. Filters: status, severity, assigned to me. Each row opens to its notes and the Assign, Dismiss and Reopen controls. `.table-wrap`, first column held, usable at 390 px; buttons show a busy label; Enter in the note field submits nothing.
- The job page, the Jobs board's Attention column, the Estimates pages and Home keep their sentences. A dismissed exception is not shown as a need: the board and Home leave it out; the job page and the estimate page list it under "Dismissed" with the note and who dismissed it.
- Home's job needs gain `PAYMENT_OTHER_CREDIT` and the three pay-application tie sentences (carried from F08.2 and F08.1), in the order the Plan proposes for the owner's yes.
- For firm users, the company picker shows each company's count of open exceptions by severity (the roadmap's "counts on the firm console"; the console itself is F19). One tenant context at a time, never a cross-tenant query (D-19's pattern).

**API**
- `GET /api/exceptions` (filters), `GET /api/exceptions/{id}`, `POST …/assign`, `POST …/notes`, `POST …/dismiss`, `POST …/reopen`; the firm count on the existing companies read. Money inside a sentence stays text. Refusals are one plain sentence. The role matrix test extended.

**Answers to the eight questions**

**1. When the run happens.** The run is one worker task, `exceptions.refresh` (`tenant_id` first, D-19), registered through `load_task_modules()`. Triggers:
- **After a QuickBooks poll applies a change**: the `qbo.normalize` task enqueues it when `applied > 0`, dedupe key `refresh` (the partial unique index on `(tenant_id, kind, dedupe_key)` over queued and running tasks collapses a poll's several entity tasks into one run, and the run's `run_after` is later than theirs so it runs after them). A poll that applies nothing enqueues nothing. Cost: one run per poll slot with changes (every 15 minutes at most, `qbo_cdc_poll_minutes`).
- **After an import loads estimates**: `process_batch` enqueues it when `counts.loaded > 0`, same key.
- **After a person's write that changes a generator's input**: an after-write hook on the API, not a list of call sites. A dependency with `yield` declared on the `/api/jobs`, `/api/change-orders`, `/api/estimates`, `/api/customers`, `/api/config`, `/api/imports` and `/api/exceptions`-free routers (the queue's own writes change no generator input) enqueues the run inside the request transaction when the method is `POST`, `PUT`, `PATCH` or `DELETE` and the handler returned without raising; it depends on the request session, so it tears down before the session commits and the `pg_notify` goes with the commit. It over-approximates (a note on a job triggers a run) and dedupes, so the cost is one run per burst of writes.
- **While a run is running**, a new trigger enqueues under the key `refresh:next` (at most one), so a change applied during a run is caught by the run after it rather than by the next poll. Two keys, at most two queued.
- **No schedule.** Nothing in scope changes with the calendar except the age in `EST_UNATTACHED`'s sentence, which is not what the sentence states (answer 3), and the next poll refreshes the text anyway.
- **A page read never runs it.** The pages compute their sentences live as today (answer 4) and read the queue's status rows; the queue page shows the rows as of the last run, with "as of" read from the latest succeeded `exceptions.refresh` task of the tenant (`task.finished_at`; no new table for it).
- **Cost of one run**: the Jobs board's reads for every job (`list_jobs`, `load_board(other=False)`: the jobs' own rows, bounded by their customer rows), the review queue, the tracked rows, the Estimates list's views plus the burden per estimate, then one read of the tenant's `exception` rows and one write per changed row. The same reads the Jobs page and the Estimates page do today, once, in the worker. Criterion 13 states 20 seconds at 1,000 estimates and 200 jobs; the observed figure goes in the build notes.
- **"Next run" to a person who has just fixed something**: the page they are looking at already shows the sentence gone (computed on read). Their write enqueued a run in the same transaction; the worker wakes on the notify and the queue row reads `resolved` within seconds (the poll fallback is 5 seconds). If a run is already queued, that run sees the fix; if one is running, the `refresh:next` run does. In tests `run_until_quiet` stands for all of this.

**2. The table, column by column, for the owner's yes.** Two tables, not one: the current state of an exception changes (status, assignment, last raised), so its row cannot be append-only; its history must be (D-13: notes and status changes are history). ## D-46 · 2026-10-08 · An exception is dismissed only with a note, never when it blocks a close, and opens again when what it states changes

**Decision**: A review sentence the platform raises is held as an exception with one of three states: open, resolved or dismissed. Only the platform sets resolved, when its generators no longer raise the exception; no person resolves one by hand. A person may dismiss an open exception of severity info or warn, and only with a note; the note, the person and the time are kept. An exception of severity block-close cannot be dismissed: it closes only when its cause is gone. A dismissed exception stays dismissed while what its sentence states is unchanged, and opens again when that changes (a different amount or a different subject), with the earlier note kept. Assign, dismiss and reopen belong to firm_admin, firm_staff and client_admin; everyone who can open the company reads the queue and adds notes. Dismissing an exception changes no figure.

**Reasoning**: The owner's answers of 2026-10-08. Dismissal exists so that a sentence a person has judged acceptable stops asking for attention, with the judgment on record (BLUEPRINT §3 principle 6). A period will not be approved while a block-close exception is open, so letting one be dismissed would be a way round the close. An amount that has changed is a new fact that the earlier note did not judge, so the exception asks again.

**Affected**: F09 (the model and the rules). F16 (period close reads severity and state). BLUEPRINT §10, §11. D-26 narrowed as to F09: the four billing-request sentences are not queued (owner, 2026-10-08); the rest of D-26 stands.
