### Goal
The owner took one job, 67 Elm Street, through the F07 screens on production: review, new job, QuickBooks link, work-area kinds. The figures were right (revised contract 465,469.59, unapproved change orders 53,704.13, EAC in the WIP basis 327,929.93). Four things on the screens got in the way, and this patch fixes those four and nothing else: the review queue cannot be opened on a chosen estimate; confirming kinds is one click per work area with no way to accept the suggestions together; the Kind and Confirm as columns do not say plainly what is suggested, what is confirmed and what a click will do; and a job's sold-on date cannot be corrected when the estimate carried no date. The estimate as it now stands on production (29 work areas) is added as a second fixture so later features are accepted against the job the owner is working. D-02 and D-36, decided 2026-10-01, are appended to the decisions file with this patch. No accounting behaviour changes: every figure the job screens compute today is computed the same way after it.

### In scope
**Review queue opens where the person is looking**
- The review view takes an optional estimate id. The "Sold, not yet reviewed" line on an estimate's detail opens the queue on that estimate, not on the first entry. An id that is no longer in the queue (already a job, no longer sold) opens the queue at its start with one sentence saying so.
- The queue page gains a labelled select, "Estimate", listing every entry in the queue (estimate id, name, price); choosing one shows it. "Skip to the next estimate" stays and still writes nothing. "Estimate n of N" stays correct after a jump.
- `GET /api/jobs/review` is unchanged; this is page state only.

**Confirm all kinds as suggested**
- New action on a job: confirm every kept work area on the latest version of the job's original estimate whose kind is not yet confirmed, each at its suggested kind (D-01: the suggestion is the platform's, the confirmation is the person's; one press by a person is a person confirming). `POST /api/jobs/{job_id}/work-areas/kinds/confirm-suggested`, `can_manage_jobs`, returns the job detail.
- One `work_area_kind_confirmed` audit row per work area confirmed, in the same transaction, with before and after as the single action writes them (the F04 "confirm all suggestions" rule: one row per item, never a summary row). A work area with no suggestion is left unconfirmed and stays in the "to confirm" count. Already-confirmed work areas are not touched. A second press with nothing left to confirm writes nothing.
- Job detail: a button above the work-area table, "Confirm all as suggested (n)", shown to managers when n > 0, disabled while a request is in flight. It is not the screen's primary action (D-22: "Save changes" stays the one primary action).

**Kind and its action, said plainly**
- Kind column: "Original (suggested)" / "Change order (suggested)" while unconfirmed, as today; once confirmed, "Original, confirmed" / "Change order, confirmed" (words first, D-22). "Omitted" unchanged.
- The "Confirm as" column is renamed "Action". An unconfirmed kept row shows two separate controls, "Confirm original" and "Confirm change order", with visible space between them (today they render as "OriginalChange order"). A confirmed row shows one control, "Change to change order" or "Change to original". The same endpoint as today; only labels and spacing change.
- The sentence under Revised contract ("n work areas to confirm") is unchanged.

**Sold on can be corrected**
- `PATCH /api/jobs/{job_id}` accepts `sold_on` (a date, not in the future in the tenant's time zone; 422 in one sentence otherwise). It is part of the existing `job_updated` audit row's before and after. The job detail form gains a labelled date field, "Sold on".
- The "(set when created)" note keeps its meaning (owner's F07 answer 17): it shows while the date did not come from the original estimate and has not been set by a person. How that is known without a new column is Claude Code's to propose in the Plan (see the questions); no migration is expected.

**How each piece is built**
1. *Review queue on a chosen estimate.* `Shell.openReview(estimateId, externalId)` sets `jobTarget = {view: "review", estimateId, externalId}`; `Jobs` passes both to `JobReview`. When the queue loads, pure `startIndex(entries, estimateId)` returns the entry's index, or 0 with `missing: true`; the page then shows one sentence, "EST6115758 is not waiting for review any more, so the queue opens at its first estimate." The labelled select "Estimate" lists every entry as `EST… · name · price` (via `estimateOption`); choosing one sets the index. "Estimate n of N" reads from the index, so it is right after a jump. `GET /api/jobs/review` is untouched; `nextIndex` and Skip are untouched.
2. *Confirm all as suggested.* `service.confirm_suggested_kinds(db, tenant_id, job_id, actor)`: the latest version of the original estimate's work areas (as `confirm_kind` loads them), kept, `kind is None`, suggestion present → set `kind`, `kind_confirmed_by`, `kind_confirmed_at`, one `work_area_kind_confirmed` row per work area with exactly `confirm_kind`'s `before`/`after`/`rows`; one flush, one transaction (the request's). A kept row with no suggestion is skipped and counted; an omitted row is never considered; nothing to do → no row, `confirmed = 0`. The selector is a small pure function over `(order_no, kept, kind, suggestion)` tuples so the "no suggestion" branch is unit-tested (see note A). The endpoint is `can_manage_jobs` and returns the job detail plus `confirmed`, `skipped` and `message` ("28 work areas confirmed as suggested." / "Nothing was left to confirm." / "27 work areas confirmed as suggested; 1 kept work area has no suggestion and is left to confirm."). Job detail: `<button className="button">Confirm all as suggested (n)</button>` above the work-area table, `n = to_confirm`, managers only, hidden at 0, disabled while busy; the message shows as a hint. "Save changes" stays the one primary action.
3. *Kind and Action.* `_kind_label`: confirmed → "Original, confirmed" / "Change order, confirmed"; unconfirmed and "Omitted" unchanged. The column header becomes "Action". Pure `kindActions(w)` returns the controls: unconfirmed kept → `Confirm original`, `Confirm change order`; confirmed original → `Change to change order`; confirmed change order → `Change to original`; omitted → none. The cell renders them inside `<span className="actions">` as separate `<button type="button" className="link-button">` elements, same endpoint and body as today. The frontend test renders the cell with `react-dom/server`'s `renderToStaticMarkup` (already a dependency; no DOM library) and asserts two `<button>` elements with the two names on an unconfirmed row and one "Change to …" on a confirmed row; to make that renderable under `node --test`, the cell is a tiny `KindActions` component in `src/kindActions.js` written with `createElement`, imported by `JobDetail.jsx` (see note B for the fallback).
4. *Sold on.* `JobPatchIn.sold_on: date | None`; `update_job` refuses a date after `tenant_today(db)` with "Sold on cannot be after today, 2026-10-01." (422); `_job_fields` already carries `sold_on`, so the existing `job_updated` row holds before and after. The form gains `<input type="date">` labelled "Sold on"; `changed` and `save` include it. The note: see question 1.
5. *Fixture tests.* A fixture that calls `make_tenant` then uploads `ELM_V2` and `run_until_quiet`; the estimate detail is asserted first (counts and figures), then the job criteria in order. The 25-row case confirms 1–3 by hand, records their `kind_confirmed_at` from the DB, presses, and compares.

**Questions the brief leaves to the Plan** (a recommendation on each; waiting for the owner's yes)

1. *How "(set when created)" is known after a person sets Sold on, without a new column.* **Recommend the audit log.** The note shows when the date did not come from the original estimate (today's rule, `estimate_date != sold_on` or no original) **and** no `job_updated` row for the job names `sold_on` in `changed_fields`. `load_job_views` adds one query over `audit_log` for the jobs on the page (`entity_type = 'job'`, `action = 'job_updated'`, `detail->'changed_fields' @> '["sold_on"]'`), so the list and the detail agree. The audit log is append-only and already the record of "a person did this", so the answer is exact and cannot drift; a pool or program keeps the note until someone sets the date (the F07 test stays true). The alternative, comparing `sold_on` with the creation date in the tenant's time zone, needs no query but is wrong whenever a person sets the date to the creation date on purpose, and the brief's wording ("has not been set by a person") is exactly what the audit row records. The query has no index on `entity_id`; at a tenant's audit-log size that is fine, and the F09 exceptions work will add one if it ever matters.

2. *F07's open criterion (the pass on all 16 sold estimates, needing P0-1).* **Recommend restating it to the owner's job-by-job approach**, in `docs/briefs/F07.md` line 68 and ROADMAP's F07 line, dated 2026-10-01: "Owner pass on jobcost.dev, job by job: 67 Elm Street through review, new job, QuickBooks link and kinds with revised contract 465,469.59 (done 2026-10-01); the other sold estimates are reviewed as the owner reaches them and are not a gate; P0-1 gates only the links."
