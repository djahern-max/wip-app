## F06.1 · Burden on estimates
**Roadmap phase**: B (a patch to F06; new ROADMAP line under F06, as F05.1 and F05.2 sit under F05) · **Blueprint refs**: §6 (labor cost), §8.1, §8.2 (same basis both sides), §8.3, §10, §14 · **Decisions**: D-04, D-05, D-22, D-23, D-32, D-34
**Status**: drafted 2026-09-29 (owner and Claude); Plan written 2026-09-29; owner's answers and go-ahead 2026-09-29; built 2026-09-29; owner's pass on jobcost.dev 2026-09-29; **closed 2026-09-29**.

### Goal
An estimate's EAC in the WIP basis carries labor burden the way D-05 and D-34 define it: for every kept work area, the Labor (slot 10) cost lines are multiplied by the burden rate in force for their division on the estimate date, quantized `ROUND_HALF_UP` to the cent per work area and division, and the result is shown as Labor Burden (slot 20). Burden is computed when the estimate is read and is never written to `estimate_cost` or any other table, so the cost lines stay exactly as loaded and their total always ties to the estimating system (D-34). The detail shows estimated cost **as estimated** and **with burden** side by side; EAC in the WIP basis is the burdened figure; there is no stored "burden applied" state anywhere. A slot-20 line that arrives on the template loads raw, is excluded from the burdened figures and raises `EST_BURDEN_LINE` (D-05). Alongside, two small screen items from the F06 Discovered list: configuration lists hide inactive rows by default, and Imports no longer defaults to a source kind.

### In scope
**Burden computation (`app/domain/estimates/burden.py` or beside the existing read path; pure function over spine state, like the F06 exception generators)**
- Input: the estimate's latest version (kept work areas and their cost lines), the tenant's active `burden_rate` rows, the date to price at. Output per kept work area: `{division_code: (labor_amount, rate, rate_effective_from, burden)}` and the work area's burden total; per estimate: burden by division, total burden, and the rate rows used (division, rate, `effective_from`, `basis_note`), so the screen and the audit reader can see which row produced the number.
- A cost line's division is the first digit of its cost code (D-23: `210` is division 2, slot 10). Lines under an omitted work area are outside burden, as they are outside every total (F06). A line whose code did not resolve through the grid (`EST_UNKNOWN_COST_CODE`) is outside burden.
- Rate in force: `burden.rate_in_force(division_id, on_date)` (F04), the active row for that division whose half-open period contains the date; a whole-company row (`division_id` null) is used only when no division row covers the date. **The date is `estimate.estimate_date`; when it is blank, the `received_at` date of the version being read** (needs a yes, question 1).
- Quantization: burden is `(Σ slot-10 amount for the work area and division) × rate`, quantized `ROUND_HALF_UP` to the cent once, per work area and division; totals are sums of quantized amounts. On 67 Elm Street this is 6,383.50, not the 6,383.51 that per-division quantization gives; a test pins the difference.
- No rate for a division on the date: burden for those lines is not computed, the estimate raises `EST_NO_BURDEN_RATE` (division, date), and the detail shows Labor Burden as "not computed" with EAC in the basis unchanged from the as-estimated figure (needs a yes, question 2).
- `EST_BURDEN_LINE`: a cost line whose slot is 20 loads and is stored like any line, appears in the as-estimated column, is excluded from the with-burden column and from EAC, and raises one exception per estimate naming the work areas that carry such lines. The generator sits with the others in `app/domain/estimates/exceptions.py`.
- Nothing is written: no new table, no column, no migration. `estimate_cost` is not touched by this feature.

**API**
- `GET /api/estimates/{id}` gains, per kept work area, `burden` (string, cents) and, per estimate, `burden_by_division` (list of `{division_code, labor_amount, rate, rate_effective_from, burden}`), `burden_total`, `cost_total_as_estimated` (unchanged figure), `cost_total_with_burden`, `eac_in_basis` (now burdened), and `eac_in_basis_as_estimated`. Money as strings with cents; the rate as a string fraction ("0.1959"). The list endpoint is unchanged.

**Screens (D-22)**
- Estimate detail, work-areas table: a **Burden** column after Cost; the totals row sums it. Cost stays as estimated.
- Estimate detail, cost by category: two amount columns, **As estimated** and **With burden**. Only the Labor Burden row differs (as estimated: whatever slot-20 lines carry, normally 0.00; with burden: the computed amount). The Labor Burden row's note names the rate(s): "EX 19.59% from 2026-01-01" (several divisions: one per line). Totals row shows both columns; the line below reads **EAC in the WIP basis** (burdened) with the as-estimated EAC beside it in smaller text, so the reviewer sees both without switching anything.
- Attention: `EST_BURDEN_LINE` and `EST_NO_BURDEN_RATE` sentences, one each, following the existing style (a sentence, not a code; cites the decision).
- Configuration lists (Accounts, Divisions, Cost categories, Burden rates): inactive rows hidden by default; a "Show inactive (n)" control above the table shows them; the choice is page state only (not stored, not per user). Nothing is deleted or changed; Deactivate still works and the row simply drops out of the default view.
- Imports: the Source select opens on an empty "Choose a source" option; Upload is disabled until one is chosen (F05 and F06 Discovered).

**Checked against the code and the fixture before planning**
- The F04 function is `burden_rate_on(db, day, division_id)` in `app/domain/config/burden.py`, not `rate_in_force`; it returns the rate only. Its rule is the one this brief wants (active rows, half-open `[effective_from, effective_to)`, division row first, whole-company row only when no division row covers the day).
- `estimate_cost` already carries `division_id` and `cost_category_id`, resolved through the grid at load; the read path (`service.load_grid`, `LineView`) already gives each line its division code and slot. Burden uses those, not a second parse of the code's first digit (same answer under D-23; a line whose code did not resolve has neither and is outside burden).
- Totals count a line only under a work area that is kept **and** priced above 0.00 (`WorkAreaIn.counts`, F06/D-32). Burden follows the same rule, so a labor line under a kept 0.00 work area is outside burden as it is outside every total (it already raises `EST_COST_LINE_ON_OMITTED`).
- EAC in the WIP basis is the sum of the categories the tenant's `wip_basis` names (`totals.compute`). Burden reaches EAC only if slot 20 is in that policy (question 5).
- `estimate_version.received_at` is a UTC timestamp. Tenants have no time-zone column; the `timezone` policy key exists and has no default (F04).
- 67 Elm Street: labor is 32,585.55, all on `210`, across 13 counting work areas; no `estimate_date`. Quantized per work area (the brief's rule, D-05's "per work area"): EX 0.1959 gives **6,383.50** (whole estimate: 6,383.51), LS 0.2136 gives **6,960.29** (whole estimate: 6,960.27), 0.2100 gives **6,842.96** (whole estimate: 6,842.97). The brief's LS and 0.2100 figures are whole-estimate quantized (question 4).
