## D-10 · 2026-09-17 · Authentication is built in the platform, not bought
**Decision**: Email + password (argon2id), TOTP mandatory for `firm_admin` and `firm_staff`, server-side sessions stored in Postgres and carried by an `HttpOnly`, `Secure`, `SameSite=Lax` cookie. No hosted identity provider.
**Reasoning**: BLUEPRINT §11 left this open. There is no self-serve signup and the user count is small. Membership, roles, and tenant switching live in the platform's database either way, so a hosted provider would add an external dependency and a vendor without removing the authorization work. Accepted cost: the platform owns password reset, lockout, recovery codes, and secret rotation.
**Affected**: F02. BLUEPRINT §11 (Auth). New dependencies `argon2-cffi`, `pyotp`, `cryptography`, frontend `qrcode`. New global table `session`. Revisit if a client requires SSO.

## D-11 · 2026-09-17 · A user reads their own memberships through a second RLS policy
**Decision**: `membership` carries one additional policy, `FOR SELECT` only, `USING (user_id = NULLIF(current_setting('app.user_id', true), '')::uuid)`, created by the migration helper `allow_own_membership_read()`. `app.user_id` is set transaction-locally by the session dependency. All writes to `membership` still pass only through `tenant_isolation`. The RLS enumeration test holds an explicit allow-list of extra policies and fails on any policy not listed. No other table may carry an extra policy without a new decision.
**Reasoning**: With RLS forced, login and the tenant switcher see zero memberships before a tenant is chosen. A bypass role is ruled out by the CLAUDE.md tenancy rules. A `SECURITY DEFINER` function would work but sits outside what the enumeration test inspects; a policy is visible in the catalog and testable.
**Affected**: F02. BLUEPRINT §11 (Isolation). CLAUDE.md Tenancy section (amended). `tests/test_rls.py`.

## D-12 · 2026-09-17 · Two audit tables
**Decision**: `audit_log` is tenant-scoped (`tenant_id NOT NULL`, RLS enabled and forced) and holds events that belong to one tenant. `firm_audit_log` is global, keyed by `firm_id`, readable only by firm roles, and holds events with no tenant: logins, lockouts, TOTP and password events, user creation. Entering a tenant writes `tenant_enter` to that tenant's `audit_log`, so a `client_admin` can see who accessed their company.
**Reasoning**: The alternative, one table with a nullable `tenant_id`, breaks the `tenant_id NOT NULL` hard rule and complicates the isolation policy. Two tables keep the tenant rule without exception and keep firm-level security events out of client view.
**Affected**: F02 and every later feature that writes audit events (§11 Audit list). `firm_audit_log` and `session` join `firm`, `tenant`, `user` as the approved tables without `tenant_id`.

## D-13 · 2026-09-17 · Insert-only tables are enforced by trigger
**Decision**: Migration helper `make_append_only(table)` installs a `BEFORE UPDATE OR DELETE` row trigger and a `BEFORE TRUNCATE` statement trigger that raise. Tables using it are listed in `APPEND_ONLY_TABLES`; a CI test fails if a listed table lacks the triggers and proves the statements fail as `app_rw` and as `app_owner`. First applied to `audit_log` and `firm_audit_log`; to be applied to the WIP snapshot tables when they are created.
**Reasoning**: F01 grants `app_rw` DML on all future tables through default privileges so that migrations never name the app role. Per-table `REVOKE` would undo that. A trigger is role-agnostic, cannot be removed by a non-owner, and can be enumerated by a test in the same way as RLS.
**Affected**: F02; the period snapshot features under BLUEPRINT §8 (approved periods immutable, snapshot tables insert-only). CLAUDE.md Tenancy and Source-of-truth sections (amended).

## D-15 · 2026-09-17 · Firm authority is an explicit row in `firm_membership`
**Decision**: New global table `firm_membership(firm_id, user_id, role ∈ {firm_admin, firm_staff})`. A user's firm role comes only from this table. For such a user, the per-tenant `membership` row grants entry to that tenant and carries no authority of its own; entering a tenant still requires one, so the client's `audit_log` shows `membership_created` and `tenant_enter` for every firm user who opens their books. Only a `firm_admin` writes `firm_membership`; every write is audited to `firm_audit_log`; the last `firm_admin` of a firm cannot be removed or demoted. `firm_audit_log.firm_id` stays nullable, because a failed login for an unknown e-mail has no firm under any model.
**Reasoning**: F02 derived firm authority from `membership`: the highest firm role on any one tenant applied to every tenant of the firm. One wrong role on one client would grant firm-wide administration, per-tenant firm roles did not mean what the schema implied, and bootstrap needed a tenant to exist before an admin could. An explicit row removes all three. Done now because the auth tables hold no real users.
**Affected**: F02.1. BLUEPRINT §11 (Shape, Roles). CLAUDE.md approved global tables. Supersedes the derivation described in the F02 CHANGELOG entry; that entry's follow-up claiming D-15 makes `firm_id` NOT NULL is corrected in the F02.1 entry.

## D-16 · 2026-09-17 · Accounts are activated only through an admin-issued one-time link
**Decision**: Users are created without a password. A `firm_admin` issues a single-use link (stored hashed, 72-hour expiry) that sets the password and, for firm users, enrols TOTP and issues recovery codes in one flow. A firm user with no TOTP enrolled cannot log in by password. Admin password reset and admin TOTP reset both work by issuing a new link. All of the user's sessions end on link redemption, password change, TOTP reset, and any `firm_membership` change.
**Reasoning**: Under F02 a firm user who had not yet enrolled could have TOTP enrolled by anyone holding their password, which defeats the second factor exactly when it matters. Watching the audit log for `totp_enrolled` detects that after the fact; the link prevents it. No e-mail is sent; the admin hands the link over directly, which is workable at this user count.
**Affected**: F02.1. BLUEPRINT §11 (Auth). Amends D-10 (enrolment path only; the rest of D-10 stands).

## D-17 · 2026-09-17 · One CPA practice per deployment
**Decision**: The platform serves one practice (the owner's) and its client companies. Rye Beach Landscaping is the first tenant. `firm` and every `firm_id` column stay in the schema so hosting a second practice is not foreclosed, but tables without tenant scope (`user`, `tenant`, `session`, `firm_membership`, `firm_audit_log`) are not isolated between firms at the database level, and there is no operator role above `firm_admin`. **Affected**: F02.1 (null-`firm_id` audit rows restricted to `firm_admin` as a low-cost guard). BLUEPRINT §11. Phase E (second tenant) is unaffected: it proves a second client, not a second firm.

## D-18 · 2026-09-17 · Reading another user's memberships from an admin request swaps `app.user_id` through one helper
**Decision**: One context-manager helper, `read_as_user()` in `app/core/auth.py`, sets `app.user_id` to the target user for the block and restores the actor's id in a `finally` block. It is callable only from the admin service (`app/auth/admin.py`), after the firm-role check, and its results are filtered to tenants of the actor's firm. Tests prove that `app.user_id` equals the actor's id after normal exit and after an exception inside the block, that an `INSERT`, `UPDATE` or `DELETE` on `membership` inside the block without tenant context still fails or matches nothing, and that no other module calls the helper.
**Reasoning**: A `firm_admin` creating a firm membership, or removing one, must know the target's client-role rows and entry rows across the firm's tenants. The D-11 policy already lets the server read a user's own rows once `app.user_id` names them (login and link redemption do this). Looping over every tenant of the firm with a tenant context each would cost one query per tenant and touch every tenant's rows for one user; the swap is one query and reads exactly that user's rows. Confining it to one helper with a guaranteed restore keeps the request from ever acting for the wrong user.
**Affected**: F02.1. CLAUDE.md Tenancy section (one sentence naming the helper and its location; pending owner approval of the wording).

## D-19 · 2026-09-17 · The worker queue is tenant-scoped and the worker polls one tenant at a time
**Decision**: `task` is a tenant table like any other (`tenant_id NOT NULL`, RLS enabled and forced, `tenant_isolation` only). The worker reads the tenant list from the global `tenant` table and, for each tenant, opens `tenant_session(engine, tenant_id)` and claims at most one due task with `FOR UPDATE SKIP LOCKED`. One transaction never holds two tenant contexts. `LISTEN/NOTIFY` with a payload of the tenant id only wakes the loop early; polling is the fallback. Task functions must take `tenant_id` as their first parameter, enforced at registration. Task payloads hold ids, never source data.
**Reasoning**: With RLS forced, a worker with no tenant context sees zero tasks. The alternatives were a global queue table (a new table without `tenant_id`, holding references into every tenant) or a second extra RLS policy for a worker setting (D-11 says no further extra policies without a decision, and any session could set it). Polling per tenant needs no exception to any tenancy rule, and at 10–30 tenants the cost is a few trivial queries every few seconds. BLUEPRINT §12 asks for a Postgres-backed queue with no Redis; this adds no dependency.
**Affected**: F03 and every later feature that enqueues work (F05 sync, F06/F11 imports, report rendering). BLUEPRINT §11 (background jobs take a tenant id explicitly), §12. CLAUDE.md Tenancy (worker rule, unchanged). Revisit if tenant count makes the poll loop measurable, or if a task that belongs to no tenant is ever needed.

## D-20 · 2026-09-17 · `raw_record` is insert-only; a change is a new version
**Decision**: Each `(tenant, source, entity_type, external_id)` has numbered versions. A new payload whose hash equals the latest version's writes nothing; a different payload writes `version + 1`; a source-reported delete writes a new version flagged `is_deleted`. No row is ever updated or deleted: the table calls `make_append_only()` and is listed in `APPEND_ONLY_TABLES` (D-13). "Current" is the highest version. JSON payloads are read with `parse_float=Decimal` and written without passing through `float`.
**Reasoning**: BLUEPRINT §6.1 says upsert by key *keeping prior versions*, and §3.4 says any report can be traced to the source row. Raw records are evidence: once periods are approved (§3.5), "what did QBO say on the day we closed" has to be answerable, and `PRIOR_PERIOD_CHANGED` (§10) needs the before and after. Making the table insert-only gives that for free and puts it under the same trigger-and-test guarantee as the audit tables. The hash check is what makes re-uploading a file or re-running a sync a no-op. The Decimal rule extends the CLAUDE.md money rule to stored payloads, where QBO amounts first arrive.
**Affected**: F03; F05, F06, F10, F11 (all write through `store_raw`); F16 (`PRIOR_PERIOD_CHANGED`). BLUEPRINT §3.4, §6.1, §7.

## D-21 · 2026-09-17 · Object storage sits behind a protocol: local in development and CI, Spaces in production
**Decision**: `ObjectStore` protocol with `LocalObjectStore` (development, tests, CI) and `S3ObjectStore` (DigitalOcean Spaces through `boto3`). The store, not the caller, builds the `tenant/{tenant_id}/` prefix. Imported files are content-addressed by SHA-256 under that prefix; original filenames are data, never part of a key. Objects are private; downloads use signed URLs with a short expiry. `S3ObjectStore` is tested with botocore's Stubber; no S3 emulator is added to compose or CI. New dependencies: `boto3`, `python-multipart`.
**Reasoning**: BLUEPRINT §11 requires tenant-prefixed private objects with short-lived signed URLs, and §12 names Spaces. Tests and CI must not need cloud credentials or a network. Having the store build the prefix means a cross-tenant key cannot be constructed by a caller's mistake. Content addressing makes a retried upload idempotent at the storage layer as well as in the database. An emulator would be one more service to operate for a thin gain over the Stubber at this stage.
**Affected**: F03; every later feature that stores files (imports, report exports, opening-balance support in F18). BLUEPRINT §11, §12. Before the first deployment the owner creates the Spaces bucket and keys, and one manual upload/download against it is recorded in OPERATIONS.md.

## D-24 · 2026-09-18 · Time-and-materials work is its own job and is not on the WIP schedule
**Decision**: Work billed by time and materials (or by the day, hour, or load without a fixed total) is set up as a separate job with contract type T&M: its own LMN estimate or rate sheet, its own QuickBooks project, its own timesheet job. A T&M job never appears on the WIP schedule and has no percent complete, earned revenue adjustment, or over/(under) billing; its revenue is what has been billed. It appears in job cost and job profitability like any other job. A fixed-price job's revised contract contains only fixed-price work areas. A unit-priced line found inside a fixed-price estimate raises an exception for the controller to resolve (move it to a T&M job, or fix its quantity and price) rather than being handled by a rule.
**Reasoning**: Percent of completion measures progress against a fixed total; T&M work has no fixed total, so including it misstates both the contract and the estimated cost (67 Elm Street: ledge removal estimated at one day, $5,475.00, billed for two, $10,950.00). Carving a line out of a job's WIP math would require cost by work area, which the ledger does not carry. Separate jobs need no allocation and work whether T&M is 2% of a project or 40%. The owner will instruct estimators and project managers accordingly.
**Affected**: F07 (job gains contract type: fixed price or T&M), F06 (exception for unit-priced lines in a fixed-price estimate), F12 (T&M jobs in profitability), F14 and F17 (excluded from WIP; shown in the tie-out as job cost outside the schedule so the ledger still ties). BLUEPRINT §5, §8 scope rules. Related: D-01, and the change-order sign-off workflow (T&M authorizations should be signed too).

## D-01 · 2026-09-18 · Change orders are work areas inside the estimate; only approved ones raise the contract
**Decision**: An estimate is a list of work areas, each kept or omitted (in LMN's Workareas + Pricing a tick means omitted), each either original scope or change order. Revised contract = price of kept original work areas + price of kept change-order work areas that are approved. EAC includes the estimated cost of every kept work area, approved or not, less the categories D-04 excludes. The baseline is the first version of the estimate the platform holds for a sold job; a work area that appears after the baseline is a change order by definition. For jobs loaded mid-stream the platform suggests the change-order flag from the name ("C/O", "CO:") and a person confirms it; a name never sets the flag on its own. A change order is approved when the customer's acceptance is on record: a signed change order (the platform exports the document and stores the signed copy), a customer e-mail, or, for work already billed, the customer's payment of the invoice that billed it. Each approval records who, when, the basis, and the document. Jobs complete and paid in full before go-live may be approved in bulk by the controller on the basis "legacy". An original work area omitted after the baseline is a deductive change: it lowers the revised contract immediately and raises an exception for the controller to confirm; if it had been billed, the exception says how much. Tenants whose estimating system issues change orders as separate estimates remain supported through the estimate's role on the job (original or change order); both forms produce the same revised contract.
**Reasoning**: Rye Beach's estimators add change orders as rows in the same LMN estimate and tick rows the customer no longer wants, so the blueprint's assumption of separate change-order estimates does not fit. Names are unreliable (one change order on the sample job has no prefix) and CLAUDE.md forbids name matching from deciding anything, so the baseline comparison does the work and names only suggest. Counting cost but not price for unapproved change orders follows the conservative treatment of unapproved change orders and makes unauthorised scope growth visible as margin fade in the month it happens, which is the control the owner asked for after a $31k job reached $50k without the customer's agreement. Deductions are recognised at once because overstating a contract is the worse error; the exception protects against a mistaken tick, which happened repeatedly on the Beauchesne job.
**Affected**: F06 (work areas parsed with kept/omitted; versions compared to the baseline), F07 (work-area kind and approval; revised contract; job contract type per D-24), a new change-order sign-off feature after F07 (export, signed copy upload, approval record), F09 (exceptions: billed-then-omitted, unapproved change order with cost, deductive change), F14, F15 (fade/gain). BLUEPRINT §5 (`estimate`, `job_estimate`; new `estimate_work_area`), §8.1. CLAUDE.md Vocabulary: revised contract = original + **approved** change orders (unchanged; "approved" now defined).

## D-04 · 2026-09-18 · WIP basis ties to division cost of goods sold; owned equipment, vehicles and fuel are outside it for now
**Decision**: For percent complete, both cost to date and EAC include only cost categories that reach jobs through the ledger today: Labor, Materials, Supplies, Subcontractors, Equipment Rental, Disposal, Permits & Bonds, and Other. Equipment (owned), Vehicles (owned), Fuel, and Equipment Maintenance are excluded from both sides. Labor Burden is in the basis only if D-05 puts it on both sides; Warranty is not decided here. Earned revenue remains percent complete × the full revised contract. No allocation entry is posted and no accounts are added. Estimated cost must therefore be captured by cost category, at least per estimate, so the excluded categories can be removed from EAC; an estimate without that split cannot enter the WIP schedule and raises an exception instead. An LMN line that mixes a person and a vehicle ("Driver Flat Rate w/ Truck") is classed as Labor, because the driver's hours are what will reach the job. Job margins shown by the platform are labelled "before owned equipment and fuel"; Job Profitability may show estimated owned-equipment cost as a memo line, never in the WIP schedule. Revisit after two clean month-end closes, moving to internal equipment rates charged to jobs by journal entry (hours × rate, offset to an equipment-cost-applied account) once machine hours by job have a reliable source.
**Reasoning**: A cost category must be in both cost to date and EAC or in neither (CLAUDE.md, WIP basis). Rye Beach's estimates price owned machines and trucks into every work area (about 30% of cost on the sample excavation work area, about 8% across the whole 67 Elm Street job) but the ledger carries those costs as depreciation, interest, repairs in overhead (6100 mechanic, 6410 parts), insurance, and shared fuel (5610–5630), none of it by job. Including them in EAC alone would understate percent complete on every job. LMN timesheets record people's hours only, so charging machines to jobs has no data source yet. LMN itself counts "Driver Flat Rate w/ Truck" hours as labor hours. The owner's priority is a WIP schedule that ties to the cost of goods sold section of the income statement; allocation is the next stage of maturity, not the first.
**Affected**: tenant_policy `wip_basis` for Rye Beach (F04 stores it); F06 (estimated cost by cost category per estimate; exception when missing); F10, F11, F12 (margin label, memo line); F13 tie-out (fuel and equipment costs sit outside job cost by design); F14. D-23 codes n45, n47, n65 stay reserved and unused. BLUEPRINT §8.1, §8.5, §14. ROADMAP "Later: owned-equipment and fuel allocation" is the revisit.

## D-26 · 2026-09-21 · Billing requests are cumulative percent complete per work area; invoice lines carry the work-area number
**Decision**: A billing request is an instruction from operations, per job, stating for each work area the cumulative percent complete to date (not the increment). The amount to bill on a work area = its price × cumulative percent − billed to date on that work area, never less than zero; a request that yields a negative amount, exceeds 100%, names an omitted work area, or names a work area priced at 0.00 (an unpriced change order) raises an exception rather than an invoice line. A request may also state a job-level instruction ("job complete, bill 100%"; "50% job start"), which applies the same percent to every kept work area. Every invoice line keyed into QuickBooks begins with "#n " where n is the work area's order number in the estimate; the platform matches invoice lines to work areas by that number, an identifier, and offers the description only as a suggestion for lines that lack it. Together with the document-number convention (estimate number + _DEP, _PMT1, _PMT2 …) this links every invoice to its job and every line to its work area without name matching. A new feature, F08.1 · Billing requests, is added to ROADMAP.md directly after F08 (an addition, nothing moved): capture the request (pasted text in the operations manager's format, or a form), compute the lines, raise the exceptions above, and produce an invoice worksheet for the controller to key into QuickBooks. The platform writes nothing to QuickBooks.
**Reasoning**: The operations manager states percent complete to date because he does not know what has been billed; only the controller and the office manager use QuickBooks. Cumulative percent is also how a schedule of values and an AIA pay application work, so the same feature serves general contractors. ## D-28 · 2026-09-22 · Deleting a tenant is an operator action outside the application, and the only exception to append-only

## D-29 · 2026-09-22 · `webhook_event` is the one ingestion table without `tenant_id`, and it is append-only
**Decision**: Intuit's webhook deliveries are stored in `webhook_event`, a table with no `tenant_id` and no row-level security, one row per event (the CloudEvents `id`, the realm, the event type, the entity id, the event object as received, Intuit's transaction id and schema version). It is insert-only (`make_append_only`, listed in `APPEND_ONLY_TABLES`, checked by `prod_check.py`), and a partial unique index on the event id makes a retried delivery store once. It is read without tenant context only in two places: the webhook route stores a delivery, and the Connections page counts the last 24 hours of deliveries for the realm of the tenant it is acting for. Which tenant holds a realm is found the way the worker finds anything: one `tenant_session` per tenant, never a query across tenants. The payload is a trigger for F05's change poll and is never used as data.
**Reasoning**: A delivery arrives before anyone knows which tenant holds the realm, and under forced RLS the application role cannot look a realm up without a tenant context; so the row cannot carry a tenant at insert, and an append-only row cannot gain one later. Storing it raw before anything reads it is the raw-before-normalized rule. Keeping the table tenant-less and small (ids and the event object; no amounts, no names) is safer than inventing a tenant for it, and the enumeration test needs the column name `tenant_id` to mean tenant scope, so the table simply must not have one. Intuit resends a delivery with the same id when it did not get a 200 within three seconds, hence the uniqueness rule.
**Affected**: F05.1 (migration 0009, `app/integrations/qbo/webhooks.py`, `scripts/prod_check.py` through `APPEND_ONLY_TABLES`). CLAUDE.md "approved tables without `tenant_id`". F10 needs no change: the same table receives the cost-entity events.

## D-30 · 2026-09-24 · Shared supplies are booked to a pool job and allocated at month end
**Decision**: A purchase that serves many jobs (hydroseed seed, mulch, tackifier, fertilizer; hardscape sand, polymeric sand, adhesive; softscape amendments) is booked to a **pool**, never split at entry. A pool is a QuickBooks project named `Pool – <material group>` under a customer of the same name (a deliberate exception to §13.2's LMN-id-first naming, since a pool has no estimate); the first is `Pool – Hydroseed`, others are created when the first shared invoice for that group arrives. In the platform a pool is a job with contract type `pool`, the third value beside fixed price and T&M (D-24), set by a person in F07 and never inferred from the name. A pool has no estimate, no contract, no percent complete; the D-04 exception for an estimate without a category split does not apply to it. The line is coded to the division's Supplies slot (5n35) like any other supplies line; no accounts are added and D-23 is unchanged. Freight and delivery on a pooled invoice go to the same pool. Ramp keeps one rule: a Customer/Project is required on every 5xxx line, and for a shared purchase that project is the pool.

At month end each pool is allocated to the jobs that consumed from it. Eligibility and driver are set per pool in `tenant_policy`. For Rye Beach initially: eligible jobs are fixed-price and T&M jobs whose LMN estimate contains a work area of that material group and that recorded labor hours in the month; the driver is labor hours on those jobs in the month. Allocation is never by revenue and never across all active jobs. Purchases are allocated in the month invoiced (invoice date = cost month); a pool with a balance at period end is an exception, not a carry-forward, until a yard-count method is adopted (revisit after two clean closes, as D-04). The platform computes the allocation and produces a formatted reclass entry (DR 5n35 by job / CR 5n35 pool job) the way §8.4 v1 produces the WIP entry; the controller posts it in QuickBooks; the platform writes nothing back. Until the posted entry is synced, allocated cost reaches jobs as `job_cost_line.basis = allocated` (§7); once synced, the QuickBooks lines are `gl_direct` and supersede the platform's allocation, and the two must agree to the cent. A period cannot be approved while any pool has a balance other than 0.00 unless waived with a note. Pool jobs never appear on the WIP schedule, backlog, or job profitability, and their cost is never unassigned.

**Reasoning**: East Coast Landscape Supply invoice #3919 (hydroseed supplies, 8,445.00, invoice date 2026-09-18) is job cost belonging to no single job. The team's first reactions were entry-time tracking systems (a Slack channel, LMN material logs); the owner's experience is that those fail within weeks. A pool with a month-end allocation is one rule the whole team can follow: one job, tag the job; many jobs, tag the pool; never guess a split. A placeholder project rather than a blank line keeps Ramp's job-required rule intact, gives the platform an external id to match, and keeps the cost out of the unassigned bucket. Separate GL accounts per material group were considered and rejected because D-23 puts detail on the line, not in the chart. Allocating by revenue across every active job would charge hydroseed to a paver job and move percent complete and fade/gain on jobs that never consumed the material (§8.2, §8.3 same-basis rule). Labor hours on eligible jobs is the only per-job activity data available: LMN timesheets record the job, not the task (D-04). Expensing on purchase front-loads cost to date when material is bought in bulk; accepted for now because in-season turnover is short. Format-and-post follows §8.4 v1 and the no-write-back rule; supplies become the first real use of `allocation` and `basis = allocated`, which the roadmap holds for owned equipment and fuel.

**Affected**: F07 (contract type gains `pool`; excluded from WIP scope, backlog, profitability). F06 (no estimate expected for a pool). F10 (pool lines are `gl_direct` with job = pool job). ## D-32 · 2026-09-25 · Estimates are built on the platform's cost codes; the platform's template is the estimate source

**Decision**: An estimate on the platform is a list of work areas (D-01), and under each work area a list of **cost lines**, each carrying one cost code (D-23), hours and an amount. A work area's estimated cost is the sum of its cost lines; the estimate's cost by cost category is the sum over kept work areas; EAC is that sum less the slots D-04 excludes. The platform publishes one estimate template (xlsx or csv; sheets *Estimates*, *Work areas*, *Estimate costs*) and that template is the only estimate source in F06. No parser is written for any estimating system's own report or paste; the `EstimateSource` protocol in BLUEPRINT §6.3 keeps one implementation. Kept work-area prices tie to the estimate price (`EST_PASTE_TOTAL_MISMATCH`); a kept work area priced above 0.00 with no cost line leaves the estimate under the D-04 exception (`EST_NO_CATEGORY_SPLIT`) until a person supplies the lines; an omitted or 0.00 work area needs none. Estimators code estimates to the tenant's cost-code grid directly; the platform never infers a code from a name or a vendor's item type. A cost code not in the tenant's grid raises an exception on the line and never rejects the file.

**Reasoning**: The cost code equals the ledger account without its leading 5 (D-23), so an estimated dollar coded 240 and the actual dollar posted to 5240 are the same thing measured at two times; EAC, cost to date and percent complete are then on one basis with no mapping between them, which is §8.2's same-basis rule at its simplest. Rye Beach's estimating tool prices labor, machines, materials and subcontractors inside one work area and shows one cost figure (67 Elm Street's Mobilization, 4,270.12, is five cost types: crew labor 386.83, driver and truck 726.19, tag trailer 162.10, portable toilet 260.00, fence rental 2,735.00); parsers that unpick that would tie the platform to one vendor's screen layout and still not yield a category split. The owner would rather change how the company estimates than build the platform around the old way: the team is taught over the 2026–27 winter and new work is estimated on the codes from spring 2027. In-flight jobs are the cost of the change and D-04 already handles them: an estimate without a split stays off the WIP schedule and says so; the controller splits the few that will still be open, one sold estimate at a time, from the item detail.

**Affected**: F06 (brief rewritten, below). BLUEPRINT §6.3 (implementations: the template only; the PDF and vendor-export implementations struck), §7 (`estimate_cost` keyed to `estimate_work_area`, not `estimate`), §13.5 (the vendor cost-by-category export is no longer needed).
