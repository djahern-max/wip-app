## F06 · Estimate import
**Roadmap phase**: B · **Blueprint refs**: §2.2, §3 (principles 1, 4, 7), §6.1, §6.3, §7 (Spine), §10, §13.5, §15 (risk 2) · **Decisions**: D-01, D-04, D-22, D-23, D-24, D-26, D-30
**Status**: drafted 2026-09-25; plan written 2026-09-25; waiting for the owner's answers to questions 1–6 and 10–13 under Plan and a go-ahead. No code yet.

### Goal
Every LMN estimate the platform will ever need is in the spine as a row it can match by external id: the estimate's id, estimator, client, jobsite, name, status and price from the Estimator Closing Report, and, for the estimates that matter, its work areas from the Workareas + Pricing paste (order number, name, kept or omitted, hours, estimated cost, price). Re-uploading the same file changes nothing; uploading a newer report or a newer paste updates by id and keeps every earlier version, so a work area that appears or disappears after the baseline is visible as a change (D-01). Dirty rows never stop a file: the row loads if it can and raises a named exception if it cannot. Nothing here touches a job, a customer, or QuickBooks: linking an estimate to a job is F07, and estimated cost **by cost category** (what D-04 needs before an estimate can enter the WIP schedule) waits on the LMN cost-code export the platform does not yet have (Plan question 1).

### In scope
**Sources (`EstimateSource.parse(file) -> list[EstimateDTO]`, BLUEPRINT §6.3, on the F03 `parse` protocol; each is a registered `SourceKind` with a D-22 label)**
- **LMN closing report** (label "LMN closing report"). The Estimator Closing Report as a tabular file: one sheet or file per estimator; the estimator's name and the report date and estimate date range come from the header, status / Estimate ID / Client Name / Jobsite / Project/Job Name / Price from the rows; the per-status totals in the header are the file's own footer and the import ties the rows to them before anything is written. Fixture: `Sales_Person_Closing_Reports.xlsx` (two sheets, William Hess and Stephanie Sanford, report date 2026-09-17). The PDF the report comes from is **not** parsed (Plan question 2).
- **LMN work areas** (label "LMN work areas"). The Workareas + Pricing paste for one estimate: columns Order, Keep / Omit (a tick means omitted, D-01), Name, Cost Code, Notes, Hrs, COGS, Price, Profit. The paste carries no estimate id inside it; the id is keyed at upload (the file name is a suggestion, never the source). Fixtures: `EST6115758_67_Elm_Street_Parking_Lot.xlsx` (21 rows) and the Turley paste `ESTEST6120638.xlsx` (32 rows; the owner adds it to `tests/fixtures/`).
- **Estimate CSV** (label "Estimate CSV"). The generic template for non-LMN tenants: the closing-report columns plus optional estimator and dates, documented in OPERATIONS.md with a sample. The same 80 rows through the CSV give the same result as the report.

**Tables (BLUEPRINT §7 Spine; D-01 adds `estimate_work_area`; all with `tenant_id`, `enable_tenant_rls`, migration `0010`)**
- `estimate`: `external_id` (the LMN id, unique per tenant and source), `source_kind`, `estimator`, `client_name`, `jobsite`, `name`, `status` as received and `status_norm` (`pending`, `sold`, `lost`, or null for an estimate known only from a paste), `price`, `report_date`, `report_range_start`, `report_range_end`, `latest_version_id`. Client and jobsite are text on the estimate; no link to `customer` (F07).
- `estimate_version`: one row per accepted upload that touched the estimate (report or paste), `import_batch_id`, `received_at`, `kept_total`, `is_baseline` (the first version the platform holds for that estimate, D-01).
- `estimate_work_area`: per version: `order_no`, `name`, `kept`, `change_order_suggested` (from the name: "CO:", "C/O", "CO " prefix; a suggestion for F07, never a decision), `hours`, `cost`, `price`, `lmn_cost_code`, `notes`. Work-area identity across versions is `order_no`, the same key D-26 puts on invoice lines.
- `estimate_cost(estimate, cost_category, hours, amount)`: created empty with its RLS and tests. Nothing in this feature writes it (Plan question 1); the D-04 exception `EST_NO_CATEGORY_SPLIT` is raised for every sold estimate until it is populated.
- Every money column `NUMERIC(14,2)`; every value parsed as `Decimal(str(cell))` and quantized `ROUND_HALF_UP` to the cent at parse, the one defined rounding point in this feature. Hours are `NUMERIC(9,2)`.

**Behaviour**
- Rows tie to the file's own totals before anything is written; a report whose rows do not sum to its footer is loaded and the batch says so (`EST_FOOTER_MISMATCH` on the batch, not the rows).
- Idempotent by external id (§6.1): the same file again is a no-op with a batch message saying so; a newer report updates status and price by id and records a new version; an estimate absent from a newer report is left as it was (a report covers a date range, not the world).
- Version comparison (D-01): a paste for an estimate that already has a baseline is compared to it by `order_no`: a kept work area not in the baseline is a change order by definition (flag set, no name needed); a baseline original work area now omitted raises `EST_DEDUCTIVE_CHANGE` with the order number and price; a kept work area whose name at an order number differs from the baseline raises `EST_WORK_AREA_RENUMBERED` rather than being re-keyed (Plan question 4).
- Exceptions, each a code plus one plain sentence (§10; the `exception` table is F09, so these are recorded the way F03/F04 record row problems and F09 adopts them, Plan question 5): `EST_NO_ID` (no Estimate ID; Plan question 3 says whether the row loads), `EST_ZERO_SOLD` (0.00 price on a Sold row only), `EST_UNIT_PRICED` (a work-area name that reads as a rate: "per Day", "per Hour", "per Load"; D-24, a suggestion for F07 to resolve), `EST_NO_CATEGORY_SPLIT` (D-04), `EST_FOOTER_MISMATCH`, `EST_DEDUCTIVE_CHANGE`, `EST_WORK_AREA_RENUMBERED`, `EST_PASTE_TOTAL_MISMATCH` (kept total of a paste differs from the closing-report price of the same id). Pending and lost rows at 0.00 load silently. An unpriced change-order row (0.00, D-26 "#26" case) loads kept with no exception; F08.1 raises on the instruction, not the row.
- Audit: `estimate_created`, `estimate_updated` (id, changed fields, version), `estimate_version_created`, one row per estimate, never one per file.
- Roles: upload by `firm_admin`, `firm_staff`, `client_admin`; read by every role; the role matrix test extended.

**Design**

*Parsing (`app/integrations/lmn/`, `app/integrations/estimate_csv.py`, shared `app/integrations/cells.py`)*
- One helper turns a cell into money: `int` → `Decimal(int)`; `float` → `Decimal(repr(value))` (the exact shortest form of what the workbook stores, as F04's `_cell_text` does); text → commas, `$` and spaces stripped, then `Decimal(text)`; anything else is unreadable. Every money value is quantized `ROUND_HALF_UP` to cents in that helper, the one rounding point of this feature; hours the same way to two places. `1599103.5499999998` becomes `1599103.55`. The F03 hygiene scan already covers `app/integrations/`; it stays the static check, and a test asserts the sums of the two sheets to the cent.
- **LMN closing report** (`lmn_closing_report`, `.xlsx` and `.csv`, one sheet per estimator; a CSV holds one estimator). Per sheet: the estimator is the text before " — Estimator Closing Report" in the first filled cell; the range and report date are parsed from the "Estimate date range: … Report date: …" line (`Mon-D-YYYY`); the totals block is read by its labels (PENDING, SOLD, LOST beside "Total price"; "Estimate total (all statuses)"); the column header row is the first row whose first two cells are "Status" and "Estimate ID"; data rows follow to the end of the sheet; blank rows and the "Source:" note are skipped without a rejection. Per row: `status` as received; `status_norm` from the upper-cased word (`PENDING` → pending, `SOLD` → sold, `LOST` → lost; another word loads with `status_norm` null, question 12); Estimate ID trimmed and upper-cased, must match `^EST\d+$`; a row with no id is a `RejectedItem` with code `EST_NO_ID` carrying the row's contents in `detail` (question 3); an unreadable price is a `RejectedItem` naming the row. After the rows: per-status sums against the totals block; a difference yields one batch-level `EST_FOOTER_MISMATCH` item with both amounts per status, and the rows still load. A `RawItem` per row: source `lmn`, entity `estimate`, external id = the LMN id, payload = the row plus the sheet header (estimator, report date, range start and end) with money as `Decimal` (the codec stores its digits).
- **LMN work areas** (`lmn_work_areas`, `.xlsx` and `.csv`; needs the upload field `estimate_id`, question 7). Header = the first row whose first cell is "Order". Columns by header text where the text is reliable (Keep / Omit, Cost Code, Notes, Hrs, COGS, Price, Profit; matched trimmed and case-folded), Order = the first column, and the **name = the first filled cell between the Keep / Omit column and the Cost Code column** (the pasted header is off by one there, above). A row is a work area when its Order cell is an integer; a row without one (a "Fuel Surcharge" line, a footer) is skipped and counted in the batch message, never a work area. Omitted = the Keep / Omit cell holds one of `OMIT_MARKS` (`✓`, `✔`, `☑`, `x`, `X`); any other non-blank value is a `RejectedItem` naming the row (question 13). Duplicate order numbers in one paste reject the second row. Notes and Cost Code (`<Unassigned>` kept as text, `lmn_cost_code`) are stored; Profit is not. One `RawItem` per paste: source `lmn`, entity `work_areas`, external id = the keyed estimate id, payload = the list of rows, so a second paste for the same id is a new raw version (D-20) and an identical re-export writes nothing.
- **Estimate CSV** (`estimate_csv`, `.csv`): header `estimate_id, status, client_name, jobsite, name, price` required, `estimator, report_date, range_start, range_end` optional (ISO dates); same row rules as the report, no totals block. A malformed price is one `RejectedItem` naming the row. Sample and column meanings in OPERATIONS.md.
- Name rules, one constant each in `app/domain/estimates/names.py`: `CHANGE_ORDER_PREFIX = r"^\s*(?:CO:|C/O\b|CO\s)"` (case-insensitive) and `UNIT_PRICE_WORDS = r"\bper\s+(?:day|hour|hr|load)\b"` (case-insensitive). Tests: 67 Elm rows 18–21 flagged and 1–17 not (13, 14 "Concrete…" included); Turley rows 23–32 flagged; only 67 Elm row 18 unit-priced.

*Raw and pipeline (F03 protocol, three small changes; every registered kind updated)*
- `SourceKind.params: tuple[UploadParam, ...]` declares upload fields (`name`, `label`, `pattern`, `hint`); `parse(stream, params)` receives them (chart of accounts, unparsed file and the test CSV take none). `/api/imports/source-kinds` returns the fields; `POST /api/imports` accepts them as extra form fields, refuses a missing or malformed one with a sentence (422), and stores them in `import_batch.params JSONB`. Uniqueness becomes `(tenant_id, source_kind, sha256, params_key)` with `params_key` text NOT NULL default `''` (the canonical `estimate_id=EST…`), so the same bytes keyed to another estimate are another batch, and a re-upload for the same estimate is the F03 duplicate.
- `RejectedItem` gains `code`, `message`, `detail` (JSON, small: ids, order numbers and amounts as strings, the row's cells for `EST_NO_ID`); the pipeline collects them into `import_batch.issues JSONB` (list) in the batch's final transaction, alongside `rows_rejected`. A batch-level item carries `row_number = None`. `ImportBatchOut.issues` returns them and the Imports page lists them under the batch, one sentence each (D-22: the sentence, never the code alone).
- `FOLLOWUP_OUTCOMES` gains `unchanged`; the follow-up message reads "Nothing changed: this report was already loaded." / "…this paste was already loaded." (`after_load_subject` "estimates").

*Normalizer (`app/domain/estimates/normalize.py`, task `estimates.normalize`, chained by `after_load` like `config.normalize_chart`)*
- For each latest raw record in the batch. Closing-report record: find `estimate` by `(tenant, source, external_id)`; create it (`estimate_created`) or, when the raw version is new to the spine, update status, status_norm, price, client, jobsite, name, estimator, report fields (`estimate_updated` with the changed fields and the version); each new raw version makes one `estimate_version` (`kind = closing_report`, `estimate_version_created`); an unchanged record (same raw version already applied) writes nothing. An estimate in the spine but absent from the file is untouched.
- Work-areas record: create the estimate if absent (`status_norm` null, price = kept total, client and jobsite null; shown as "Not on a closing report"); otherwise leave the report fields alone. Each new raw version makes one `estimate_version` (`kind = work_areas`, `kept_total`) with its `estimate_work_area` rows (full snapshot per version; identity `order_no`). `estimate.price` is set from the kept total only while the estimate has no closing-report price.
- Version comparison is a pure function (`app/domain/estimates/versions.py`): new paste vs the baseline by `order_no` → (a) kept and not in the baseline: `change_order_suggested = true` by definition; (b) baseline original, now omitted: `EST_DEDUCTIVE_CHANGE` with order and price; (c) kept, same order, different name (trimmed, case-folded): `EST_WORK_AREA_RENUMBERED`, nothing re-keyed. **Baseline** = the first version of the estimate that carries work areas (question 11): a report-only version has no work areas to compare against.
- Cross-check: when the estimate has a closing-report price and the paste's kept total differs, `EST_PASTE_TOTAL_MISMATCH` with both amounts.
- Idempotent and re-runnable: the task re-run on an applied batch finds every raw version already applied and reports `unchanged`. Superseding is not needed (rows update by id, never by "absent from the file").

*Tables (migration 0010; `enable_tenant_rls` on all four; every FK `ondelete=RESTRICT`)*
- `estimate`: `id`, `tenant_id`, `source` (lmn | csv), `external_id` (unique per tenant and source), `source_kind` (the kind that created it), `estimator`, `client_name`, `jobsite`, `name`, `status`, `status_norm` (pending | sold | lost | NULL, CHECK), `price` NUMERIC(14,2) NOT NULL, `report_date`, `report_range_start`, `report_range_end` (DATE, nullable), `latest_version_id` (FK, nullable), `created_at`, `updated_at`. Index `(tenant_id, status_norm)`, `(tenant_id, estimator)`.
- `estimate_version`: `id`, `tenant_id`, `estimate_id`, `version_no` (unique per estimate), `kind` (closing_report | work_areas | csv), `import_batch_id`, `raw_record_id`, `received_at`, `kept_total` NUMERIC(14,2) nullable, `is_baseline` bool.
